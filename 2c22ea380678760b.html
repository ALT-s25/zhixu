一、什么是事务

1.1 生活类比：银行转账

想象你从 A 账户向 B 账户转账 1000 元。 整个操作需要两步：

  • 第一步：A 账户 减少 1000 元
  • 第二步：B 账户 增加 1000 元

如果第一步成功，第二步因为系统崩溃失败了，A 的钱少了，B 的钱没有多，这显然是灾难性的。

事务 就是用来保证：这两步要么全部成功，要么全部失败回滚，永远不会出现中间状态。

1.2 事务的定义

事务（Transaction）是数据库中一组逻辑操作的集合，这些操作被当作一个不可分割的整体来执行。

通俗理解：

  • 事务就是一个"任务包"，包里的操作要么全做，要么全不做。
  • 中途出错？自动"撤销"回到操作前的状态。

二、ACID 四大特性

ACID 是事务必须满足的四个核心特性，是数据库保证数据正确性的基石。

2.1 原子性（Atomicity）

一个事务中的所有操作，要么全部完成，要么全部不完成。

生活类比： 就像你下单购物，系统要么同时完成"扣你的钱"和"减商品库存"，要么一件都不做，不会只扣了你的钱却没减库存。

技术说明：

  • 通过 undo log（回滚日志） 实现
  • 事务执行前，MySQL 会记录每个操作的"反向操作"
  • 一旦事务失败，就按照 undo log 逐步撤销

2.2 一致性（Consistency）

事务执行前后，数据库的状态必须保持一致，所有规则（约束）都不能被破坏。

生活类比： 转账前，A 有 500 元，B 有 500 元，总计 1000 元。转账后，A 有 200 元，B 有 800 元，总计仍然是 1000 元。总金额必须守恒，这就是一致性。

技术说明：

  • 一致性是事务的目的，原子性、隔离性、持久性是手段
  • 违反约束（如外键约束、唯一约束）会导致事务回滚，以保证一致性

2.3 隔离性（Isolation）

多个事务并发执行时，每个事务都感觉不到其他事务的存在，互不干扰。

生活类比： 两个收银员同时查看仓库库存，你正在下单减库存，但收银员 B 看到的库存不应该是你操作到一半的"中间状态"。

技术说明：

  • 通过锁机制和 MVCC（多版本并发控制） 实现
  • 隔离程度由"隔离级别"控制（见后文）

2.4 持久性（Durability）

事务一旦提交，它对数据库的改变就是永久的，即使系统崩溃也不会丢失。

生活类比： 转账成功后，哪怕银行服务器立刻断电，你的转账记录也不会消失，因为已经写入了磁盘。

技术说明：

  • 通过 redo log（重做日志） 实现
  • 事务提交时，先写入 redo log（磁盘），再修改数据文件
  • 即使崩溃，重启后可以通过 redo log 恢复数据

三、事务操作语句

3.1 基本语法

sql
-- ===== 开启事务 =====
BEGIN;              -- 推荐写法
-- 或者
START TRANSACTION;  -- 效果相同，更明确

-- ===== 提交事务（确认所有操作永久生效）=====
COMMIT;

-- ===== 回滚事务（撤销所有操作回到事务开始前）=====
ROLLBACK;

3.2 自动提交模式

sql
-- 查看当前是否开启自动提交（默认是 ON）
SHOW VARIABLES LIKE 'autocommit';
-- 结果：ON 表示每条 SQL 自动提交，不需要手动 COMMIT

-- 关闭自动提交（当前 session 生效）
SET autocommit = 0;  -- 0 = OFF，1 = ON

-- 注意：关闭自动提交后，每次操作都需要手动 COMMIT 或 ROLLBACK

小提示： 实际项目中，大多数驱动/框架会自动管理事务，你只需要在需要的地方显式开启事务。

3.3 保存点（SAVEPOINT）

sql
-- 在事务中设置"检查点"，可以回滚到某个检查点而不是回滚整个事务
BEGIN;

INSERT INTO orders (user_id, amount) VALUES (1, 500);
SAVEPOINT sp1;  -- 设置保存点 sp1

INSERT INTO orders (user_id, amount) VALUES (2, 300);
SAVEPOINT sp2;  -- 设置保存点 sp2

-- 假设后续操作出错，只回滚到 sp1（保留第一条插入）
ROLLBACK TO SAVEPOINT sp1;

-- 最终提交（只有第一条插入生效）
COMMIT;

四、事务并发问题

当多个事务同时运行时，可能会出现以下问题（隔离性不够时才会出现）。

4.1 脏读（Dirty Read）

一个事务读到了另一个事务"尚未提交"的数据。

图解：

text
时间线：
事务A                           事务B
                                BEGIN;
                                UPDATE accounts SET balance=0 WHERE id=1;
                                -- 未提交！
BEGIN;
SELECT balance FROM accounts WHERE id=1;
-- 读到了 0（脏数据！）
                                ROLLBACK; -- B 回滚了，数据其实还是原来的值
-- 但 A 读到的是错误的 0
COMMIT;

危害： 读到了不真实的数据，可能基于错误数据做出错误决策。

类比： 你同事在草稿纸上写了一个未确认的方案给你看，你直接按草稿实施，结果同事后来删掉了草稿，说那是错误方案。

4.2 不可重复读（Non-Repeatable Read）

同一事务中，两次读取同一条数据，结果不一样（因为其他事务在期间修改并提交了）。

图解：

text
时间线：
事务A                           事务B
BEGIN;
SELECT balance FROM accounts WHERE id=1;
-- 结果：1000
                                BEGIN;
                                UPDATE accounts SET balance=500 WHERE id=1;
                                COMMIT; -- B 提交了修改
SELECT balance FROM accounts WHERE id=1;
-- 结果：500（和第一次读的不一样！）
COMMIT;

危害： 同一事务内数据前后不一致，逻辑混乱。

与脏读的区别：

  • 脏读：读到的是未提交的数据
  • 不可重复读：读到的是已提交的数据，但同一事务内两次读结果不同

类比： 你上午查了一下银行余额是 1000 元，下午同一笔查询结果变成 500 元，因为你老婆中间取了 500 元。同一次查询，结果变了。

4.3 幻读（Phantom Read）

同一事务中，两次查询返回的行数不一样（因为其他事务在期间插入或删除了数据）。

图解：

text
时间线：
事务A                           事务B
BEGIN;
SELECT * FROM orders WHERE user_id=1;
-- 返回 3 行
                                BEGIN;
                                INSERT INTO orders (user_id, amount) VALUES (1, 100);
                                COMMIT; -- B 插入了一行
SELECT * FROM orders WHERE user_id=1;
-- 返回 4 行（多了一行"幻影"数据！）
COMMIT;

危害： 同一事务内，查询出来的数据集不稳定，像"见鬼"一样多了行数据。

与不可重复读的区别：

  • 不可重复读：同一行数据，两次读取值不同（UPDATE 导致）
  • 幻读：同一条件查询，两次读取行数不同（INSERT/DELETE 导致）

类比：

  • 不可重复读：你数钱，数了两次，第一次 100 张，第二次 50 张，张数变了（有人拿走了）
  • 幻读：你数人头，数了两次，第一次 10 人，第二次 11 人，人数变了（有人悄悄进来了）

五、四种隔离级别

SQL 标准定义了四种事务隔离级别，隔离级别越高，并发能力越低，但数据越安全。

5.1 READ UNCOMMITTED（读未提交）

  • 能读到未提交的数据
  • 问题： 脏读 ✓、不可重复读 ✓、幻读 ✓（三个问题都有）
  • 使用场景： 几乎不用，仅对数据准确性要求极低时使用
sql
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

5.2 READ COMMITTED（读已提交）

  • 只能读到已提交的数据（解决了脏读）
  • 问题： 不可重复读 ✓、幻读 ✓
  • 使用场景： Oracle/SQL Server 的默认级别，适合读多写少场景
sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

5.3 REPEATABLE READ（可重复读）⭐ MySQL 默认

  • 同一事务内多次读取结果一致（解决了脏读、不可重复读）
  • 理论上有幻读问题，但 MySQL 通过 MVCC + 间隙锁基本解决了幻读
  • 使用场景： MySQL 默认，大多数业务场景适用
sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- 查看当前隔离级别
SELECT @@transaction_isolation;

5.4 SERIALIZABLE（串行化）

  • 最高隔离级别，所有事务串行执行（所有问题都解决）
  • 问题： 性能极差，高并发下大量锁等待
  • 使用场景： 对数据一致性要求极高且并发量很低的场景
sql
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;

六、隔离级别 vs 并发问题对照表

隔离级别 脏读 不可重复读 幻读 性能
READ UNCOMMITTED ❌ 存在 ❌ 存在 ❌ 存在 ⭐⭐⭐⭐⭐
READ COMMITTED ✅ 解决 ❌ 存在 ❌ 存在 ⭐⭐⭐⭐
REPEATABLE READ（默认） ✅ 解决 ✅ 解决 ⚠️ 基本解决 ⭐⭐⭐
SERIALIZABLE ✅ 解决 ✅ 解决 ✅ 解决 ⭐

⚠️ MySQL 在 REPEATABLE READ 级别下，通过 MVCC + 间隙锁（Gap Lock）基本解决了幻读问题。

七、乐观锁 vs 悲观锁

7.1 悲观锁（Pessimistic Lock）

假设冲突一定会发生，每次操作前都先加锁。

类比： 你去图书馆借书，不管有没有人要借这本书，你直接把书锁进抽屉，别人就借不到了，等你还回来才能借。

实现方式：

sql
-- 使用 SELECT ... FOR UPDATE 加排他锁
BEGIN;

-- 查询并锁定这一行（其他事务无法修改此行，直到本事务提交）
SELECT balance FROM accounts WHERE id=1 FOR UPDATE;

-- 执行修改
UPDATE accounts SET balance = balance - 100 WHERE id=1;

COMMIT;
-- 锁释放，其他事务才能操作 id=1 的行

特点：

  • 安全性高，不会出现并发冲突
  • 性能较低，高并发下锁竞争严重
  • 适合写多读少、冲突概率高的场景

7.2 乐观锁（Optimistic Lock）

假设冲突很少发生，操作完成后检查是否有冲突，有冲突则重试。

类比： 你和同事同时编辑同一个文档，你们各自修改，提交时系统检查"你修改时文档的版本"和"现在的版本"是否一致，不一致就提示你重新编辑。

实现方式（版本号机制）：

sql
-- 表结构（增加 version 字段）
CREATE TABLE products (
    id       INT PRIMARY KEY AUTO_INCREMENT,
    name     VARCHAR(100),
    stock    INT,
    version  INT DEFAULT 0  -- 版本号，每次更新 +1
);

-- ===== 乐观锁操作流程 =====

-- 第一步：读取数据，记录当前版本号
SELECT id, stock, version FROM products WHERE id=1;
-- 假设返回：id=1, stock=100, version=5

-- 第二步：更新时，携带版本号作为条件
UPDATE products 
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;  -- 关键！版本号必须匹配
-- 如果返回影响行数 = 1，说明更新成功（无并发冲突）
-- 如果返回影响行数 = 0，说明有其他事务已经修改了数据，需要重试

-- 应用层检查更新结果
-- affected_rows == 1 → 成功
-- affected_rows == 0 → 冲突，重新读取并重试

特点：

  • 不加锁，性能高
  • 适合读多写少、冲突概率低的场景
  • 需要在应用层处理冲突重试逻辑

7.3 两者对比

乐观锁 悲观锁
锁机制 无锁（版本号/CAS） 数据库锁
并发性能 高 低
适用场景 读多写少 写多读少
冲突处理 应用层重试 等待锁释放
实现方式 版本号/时间戳字段 SELECT FOR UPDATE

八、完整代码示例：转账业务事务

sql
-- ===== 准备工作：创建账户表 =====
CREATE TABLE accounts (
    id       INT PRIMARY KEY AUTO_INCREMENT,  -- 账户ID
    username VARCHAR(50) NOT NULL,            -- 用户名
    balance  DECIMAL(10, 2) NOT NULL DEFAULT 0, -- 余额（精确到分）
    version  INT NOT NULL DEFAULT 0           -- 乐观锁版本号
);

-- 插入测试数据
INSERT INTO accounts (username, balance) VALUES
('Alice', 1000.00),  -- Alice 有 1000 元
('Bob',   500.00);   -- Bob 有 500 元

-- ===== 转账事务：Alice 向 Bob 转 300 元 =====

BEGIN;  -- 开启事务

-- 第一步：检查 Alice 余额是否足够（使用悲观锁，防止并发超扣）
SELECT balance FROM accounts WHERE id=1 FOR UPDATE;
-- 假设返回 1000.00，满足条件

-- 第二步：扣减 Alice 账户
UPDATE accounts 
SET balance = balance - 300.00 
WHERE id = 1 AND balance >= 300.00;  -- 加余额条件，双重保险

-- 检查是否成功（在实际代码中用 affected_rows 判断）
-- 如果 affected_rows = 0，说明余额不足，需要 ROLLBACK

-- 第三步：增加 Bob 账户
UPDATE accounts 
SET balance = balance + 300.00 
WHERE id = 2;

-- 第四步：提交事务（两步操作全部成功才提交）
COMMIT;

-- ===== 验证结果 =====
SELECT id, username, balance FROM accounts;
-- 期望：Alice=700, Bob=800


-- ===== 模拟失败场景：余额不足时回滚 =====

BEGIN;

SELECT balance FROM accounts WHERE id=1 FOR UPDATE;
-- 假设余额是 100，但要转 500，不够

-- 检查余额
SET @alice_balance = (SELECT balance FROM accounts WHERE id=1);

-- 余额不足，回滚
-- （实际代码中由应用层判断并执行 ROLLBACK）
ROLLBACK;  -- 撤销所有操作，数据恢复原样

SELECT id, username, balance FROM accounts;  -- 数据不变
sql
-- ===== 使用存储过程封装转账逻辑（生产推荐）=====

DELIMITER $$

CREATE PROCEDURE transfer(
    IN from_id  INT,      -- 转出账户ID
    IN to_id    INT,      -- 转入账户ID
    IN amount   DECIMAL(10,2),  -- 转账金额
    OUT result  VARCHAR(50)     -- 结果信息
)
BEGIN
    DECLARE from_balance DECIMAL(10,2);  -- 转出方余额
    DECLARE EXIT HANDLER FOR SQLEXCEPTION  -- 异常处理器
    BEGIN
        ROLLBACK;  -- 出现任何 SQL 异常，自动回滚
        SET result = 'ERROR: 转账失败，已回滚';
    END;

    -- 开启事务
    START TRANSACTION;

    -- 锁定转出账户，读取余额
    SELECT balance INTO from_balance 
    FROM accounts 
    WHERE id = from_id 
    FOR UPDATE;

    -- 检查余额是否充足
    IF from_balance < amount THEN
        ROLLBACK;
        SET result = 'ERROR: 余额不足';
    ELSE
        -- 扣减转出账户
        UPDATE accounts SET balance = balance - amount WHERE id = from_id;
        -- 增加转入账户
        UPDATE accounts SET balance = balance + amount WHERE id = to_id;

        COMMIT;  -- 提交事务
        SET result = CONCAT('SUCCESS: 成功转账 ', amount, ' 元');
    END IF;
END$$

DELIMITER ;

-- 调用存储过程
CALL transfer(1, 2, 300.00, @result);
SELECT @result;  -- 查看结果

九、常见报错

9.1 死锁（Deadlock）

报错信息：

text
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

原因： 两个事务互相等待对方释放锁。

text
事务A 锁定了 row1，等待 row2
事务B 锁定了 row2，等待 row1
→ 相互等待，形成死锁

解决方案：

sql
-- 1. 保持固定的加锁顺序（如：总是先锁 id 小的再锁 id 大的）
-- 2. 缩短事务执行时间，减少持锁时长
-- 3. 查看死锁日志
SHOW ENGINE INNODB STATUS;  -- 查看最近一次死锁信息

9.2 锁等待超时

报错信息：

text
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

原因： 事务等待锁的时间超过了 innodb_lock_wait_timeout（默认 50 秒）。

解决方案：

sql
-- 查看锁等待超时时间
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';

-- 临时调整超时时间（当前 session）
SET SESSION innodb_lock_wait_timeout = 30;  -- 30秒

-- 查看当前有哪些锁等待
SELECT * FROM information_schema.INNODB_TRX;         -- 当前活跃事务
SELECT * FROM information_schema.INNODB_LOCK_WAITS;  -- 锁等待情况

9.3 事务未提交导致的问题

现象： 操作了数据但别的会话看不到变化。

原因： 忘记执行 COMMIT，或者 autocommit=0 时每次都要手动提交。

解决方案：

sql
-- 检查 autocommit 设置
SHOW VARIABLES LIKE 'autocommit';

-- 如果忘记提交，查看当前事务状态
SELECT * FROM information_schema.INNODB_TRX;
-- 找到对应事务后，在对应连接执行 COMMIT 或 ROLLBACK

十、面试常问

Q1：ACID 分别是什么？用自己的话解释

参考回答：

  • 原子性（A）： 事务是最小执行单元，要么全部成功，要么全部回滚，不存在"做了一半"的状态。底层由 undo log 保证。
  • 一致性（C）： 事务前后，数据库数据符合所有预定义规则（约束、业务逻辑），不会出现违反规则的状态。是事务的最终目的。
  • 隔离性（I）： 并发执行的事务互不干扰，每个事务感觉像是在独占数据库。由锁机制和 MVCC 保证。
  • 持久性（D）： 已提交的事务，其修改永久保存，即使系统崩溃也不丢失。由 redo log 保证。

Q2：MySQL 默认隔离级别是什么？为什么？

参考回答： MySQL InnoDB 默认使用 REPEATABLE READ（可重复读）。

原因：

  1. 解决了脏读和不可重复读，兼顾了数据安全性和并发性能
  2. MySQL 通过 MVCC 实现了无锁的快照读，性能比 SERIALIZABLE 高很多
  3. 通过 Gap Lock（间隙锁）和 Next-Key Lock 在很大程度上解决了幻读问题

Q3：幻读和不可重复读有什么区别？

参考回答：

不可重复读 幻读
现象 同一行数据两次读取值不同 同一条件两次查询行数不同
原因 其他事务执行了 UPDATE 其他事务执行了 INSERT/DELETE
解决方式 REPEATABLE READ SERIALIZABLE 或 Gap Lock

类比： 不可重复读是"同一个苹果，昨天是红的，今天是黄的"；幻读是"昨天数了 10 个苹果，今天数了 11 个，多了一个幻影苹果"。

Q4：什么时候用乐观锁，什么时候用悲观锁？

参考回答：

  • 乐观锁： 适用于读多写少、冲突概率低的场景（如用户信息更新、文章编辑）。用版本号或时间戳实现，无数据库锁，并发性能高。
  • 悲观锁： 适用于写多读少、冲突概率高的场景（如库存扣减、余额转账）。用 SELECT FOR UPDATE 加锁，安全但性能低。

Q5：MVCC 是什么？（进阶）

参考回答： MVCC（Multi-Version Concurrency Control，多版本并发控制）是 MySQL InnoDB 在 REPEATABLE READ 和 READ COMMITTED 级别下实现事务隔离的核心机制。

核心思想：

  • 不直接修改数据，而是保留数据的多个历史版本
  • 读操作读取的是事务开始时刻的快照版本（快照读）
  • 写操作创建数据的新版本，不影响正在读取旧版本的事务

好处：读写不相互阻塞，大幅提升并发性能。

知识点 核心内容

ACID 原子性/一致性/隔离性/持久性
操作语句 BEGIN → 操作 → COMMIT/ROLLBACK
