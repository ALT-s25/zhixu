三、发送者可靠性 ⭐⭐⭐

3.1 生产者重试机制

连接 MQ 失败时自动重试（阻塞式，会影响性能）：

yaml
spring:
  rabbitmq:
    connection-timeout: 1s
    template:
      retry:
        enabled: true
        initial-interval: 1000ms  # 初始等待时间
        multiplier: 1             # 下次等待 = 上次 × multiplier
        max-attempts: 3           # 最大重试次数

⚠ 重试是阻塞式的，对性能有影响，非网络不稳定环境建议不开启。

3.2 生产者确认机制

RabbitMQ 提供两种回执：

机制 触发时机 含义
Publisher Confirm（ACK） 消息成功投递到交换机并入队 投递成功
Publisher Confirm（NACK） MQ 内部故障 投递失败
Publisher Return 消息到达交换机但路由失败 路由失败（但 Confirm 还是 ACK）

3.2.1 开启配置

yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated  # none/simple/correlated
    publisher-returns: true
  • none：关闭确认
  • simple：同步阻塞等待回执
  • correlated：异步回调（推荐）

3.2.2 ReturnCallback（路由失败回调）

java
@Slf4j
@AllArgsConstructor
@Configuration
public class MqConfig {
    private final RabbitTemplate rabbitTemplate;

    @PostConstruct
    public void init() {
        rabbitTemplate.setReturnsCallback(returned -> {
            log.error("消息路由失败：exchange={}, routingKey={}, reason={}",
                returned.getExchange(), returned.getRoutingKey(), returned.getReplyText());
            // 可以在这里重新投递或记录日志
        });
    }
}

3.2.3 ConfirmCallback（投递结果回调）

java
// 每条消息发送时设置
CorrelationData cd = new CorrelationData();
cd.getFuture().addCallback(new ListenableFutureCallback<CorrelationData.Confirm>() {
    @Override
    public void onSuccess(CorrelationData.Confirm result) {
        if (result.isAck()) {
            log.debug("消息投递成功，收到 ACK");
        } else {
            log.error("消息投递失败，收到 NACK，原因：{}", result.getReason());
            // 重新投递 / 记录到数据库
        }
    }
    @Override
    public void onFailure(Throwable ex) {
        log.error("消息投递异常", ex);
    }
});

rabbitTemplate.convertAndSend("exchange", "routingKey", message, cd);

💡 生产者确认会消耗 MQ 性能，只在消息可靠性要求极高时开启，且仅开启 Confirm 即可（Return 触发大多是编程错误）。

四、MQ 可靠性 ⭐⭐

4.1 数据持久化

三种持久化全部要配置才能保证消息不丢失：

java
// 交换机持久化（默认已持久化）
ExchangeBuilder.directExchange("my.exchange").durable(true).build();

// 队列持久化
QueueBuilder.durable("my.queue").build();

// 消息持久化（Spring 默认已设置）
// DeliveryMode.PERSISTENT

⚠ SpringAMQP 通过注解 @Queue(durable="true") 创建的队列默认持久化。

4.2 LazyQueue 惰性队列 ⭐⭐

问题：默认队列数据存内存，消息堆积时会触发 PageOut（刷盘），阻塞所有消息处理。

LazyQueue 特点：

  • 消息直接存磁盘，内存只保留少量索引
  • 支持数百万条消息积压
  • 3.12+ 版本已是默认模式
java
// 代码声明 Lazy 队列
@Bean
public Queue lazyQueue() {
    return QueueBuilder.durable("lazy.queue").lazy().build();
}

// 注解声明
@RabbitListener(queuesToDeclare = @Queue(
    name = "lazy.queue",
    durable = "true",
    arguments = @Argument(name = "x-queue-mode", value = "lazy")
))
public void listenLazy(String msg) { }

五、消费者可靠性 ⭐⭐⭐

5.1 消费者确认机制（ACK）

MQ 投递消息给消费者后，等待消费者确认：

确认方式 含义 MQ 行为
ACK 处理成功 删除消息
NACK 处理失败 重新投递（或丢弃）
REJECT 拒绝 重新投递或丢弃
yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto  # none/manual/auto
  • none：不确认，消息投递即删除（不安全）
  • manual：手动确认（代码复杂）
  • auto：自动（无异常 → ACK，有异常 → NACK，推荐）

5.2 失败重试机制 ⭐

消费者处理失败后，默认会无限重投，CPU 飙升。配置本地重试：

yaml
spring:
  rabbitmq:
    listener:
      simple:
        retry:
          enabled: true
          initial-interval: 1000ms  # 初始等待
          multiplier: 1
          max-attempts: 3           # 最大重试 3 次
          stateless: true           # 无状态重试（有事务用 false）

重试 3 次后仍失败 → 触发失败处理策略

5.3 失败处理策略 ⭐

java
@Bean
public MessageRecoverer republishMessageRecoverer(RabbitTemplate rabbitTemplate) {
    // 重试耗尽后，将失败消息投递到指定交换机（error 队列）
    return new RepublishMessageRecoverer(rabbitTemplate, "error.direct", "error");
}
策略 类 行为
丢弃（默认） RejectAndDontRequeueRecoverer 直接丢弃
重新入队 ImmediateRequeueMessageRecoverer 重新入队（可能死循环）
投到 error 队列 RepublishMessageRecoverer 推荐，人工处理

5.4 业务幂等性 ⭐⭐⭐

问题：消息可能因网络问题被重复投递，消费者需保证同一消息处理多次结果相同。

方案一：唯一消息 ID

java
// 发送时设置唯一 ID
CorrelationData cd = new CorrelationData(UUID.randomUUID().toString());
rabbitTemplate.convertAndSend("exchange", "key", msg, cd);

// 消费时检查 ID
@RabbitListener(queues = "queue")
public void listen(String msg, Message message) {
    String msgId = message.getMessageProperties().getMessageId();
    // 查 Redis/DB，ID 已存在则跳过
    if (redisTemplate.opsForValue().setIfAbsent("mq:msg:" + msgId, "1", 1, TimeUnit.DAYS)) {
        // 首次处理
        doProcess(msg);
    }
    // 重复消息直接忽略
}

方案二：业务判断（更推荐）

java
// 下单业务幂等性：先查订单状态，已处理则跳过
@RabbitListener(queues = "pay.success.queue")
public void handlePaySuccess(Long orderId) {
    Order order = orderService.getById(orderId);
    if (order == null || order.getStatus() != OrderStatus.UNPAID) {
        return; // 已处理过，幂等跳过
    }
    orderService.updateStatus(orderId, OrderStatus.PAID);
}

💡 业务判断方案更可靠，不依赖消息 ID，推荐优先使用。

六、延迟消息 ⭐⭐⭐

6.1 死信交换机（Dead Letter Exchange）

消息变成"死信"的三种情况：

  1. 消费者 REJECT/NACK 且 requeue=false
  2. 消息在队列中过期（TTL 超时）
  3. 队列消息数超过上限

TTL + 死信 实现延迟：

java
@Bean
public Queue ttlQueue() {
    return QueueBuilder.durable("ttl.queue")
        .ttl(10000)                    // 消息 10秒 过期
        .deadLetterExchange("dl.direct")  // 死信交换机
        .deadLetterRoutingKey("dl")       // 死信 routingKey
        .build();
}

@Bean
public Queue dlQueue() {
    return QueueBuilder.durable("dl.queue").build();
}

⚠ 缺点：TTL 是固定的，无法按消息设置不同延迟时间（前面的消息阻塞后面的）。

6.2 DelayExchange 插件（推荐）⭐⭐

安装（需要 RabbitMQ 插件）：

bash
docker exec -it mq rabbitmq-plugins enable rabbitmq_delayed_message_exchange

声明延迟交换机：

java
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "delay.queue", durable = "true"),
    exchange = @Exchange(
        name = "delay.direct",
        delayed = "true",    // 开启延迟
        type = ExchangeTypes.DIRECT
    ),
    key = "delay"
))
public void listenDelayQueue(String msg) {
    log.info("延迟消息到达：{}", msg);
}

发送延迟消息：

java
@Test
void testDelayMessage() {
    rabbitTemplate.convertAndSend("delay.direct", "delay", "Hello Delay", msg -> {
        msg.getMessageProperties().setDelay(10000); // 延迟 10秒
        return msg;
    });
}

💡 DelayExchange 消息存在交换机内存中，RabbitMQ 重启会丢失！生产环境要配合持久化。

七、实战：订单超时自动取消 ⭐⭐

流程：下单 → 发送延迟消息（30分钟）→ 消费者查支付状态 → 未支付则取消订单

java
// 定义常量
public interface MqConstants {
    String PAY_EXCHANGE = "pay.topic";
    String DELAY_EXCHANGE = "trade.delay.topic";
    String DELAY_ORDER_QUEUE = "trade.order.delay.queue";
    String DELAY_ORDER_ROUTING_KEY = "order.query";
}

// 下单时发延迟消息
@Service
public class OrderService {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    public Long createOrder(OrderFormDTO orderDTO) {
        // 保存订单...
        Long orderId = saveOrder(orderDTO);

        // 发送延迟消息（20分钟后检查支付状态）
        rabbitTemplate.convertAndSend(
            MqConstants.DELAY_EXCHANGE,
            MqConstants.DELAY_ORDER_ROUTING_KEY,
            orderId,
            msg -> {
                msg.getMessageProperties().setDelay(1200000); // 20分钟
                return msg;
            });
        return orderId;
    }
}

// 消费者：检查支付状态，未支付则取消
@Component
public class OrderDelayMessageListener {
    @Autowired
    private OrderService orderService;

    @RabbitListener(bindings = @QueueBinding(
        value = @Queue(name = MqConstants.DELAY_ORDER_QUEUE, durable = "true"),
        exchange = @Exchange(name = MqConstants.DELAY_EXCHANGE, delayed = "true",
                             type = ExchangeTypes.TOPIC),
        key = MqConstants.DELAY_ORDER_ROUTING_KEY
    ))
    public void listenOrderDelayMessage(Long orderId) {
        // 查询支付状态
        Order order = orderService.getById(orderId);
        if (order == null || order.getStatus() != OrderStatus.UNPAID) {
            return; // 已支付，忽略
        }
        // 取消订单
        orderService.cancelOrder(orderId);
        log.info("订单 {} 超时未支付，自动取消", orderId);
    }
}

八、MQ 可靠性全链路总结 ⭐⭐

text
生产者
  ├── 重试机制：网络故障自动重试
  └── 生产者确认：NACK 时补偿重发

MQ
  ├── 交换机持久化
  ├── 队列持久化
  ├── 消息持久化
  └── LazyQueue：防止消息堆积崩溃

消费者
  ├── ACK 自动确认：异常时 NACK 重投
  ├── 本地重试：最多 3 次
  ├── RepublishMessageRecoverer：失败进 error 队列人工处理
  └── 业务幂等性：防重复消费

九、面试常问 ⭐⭐⭐

💡 如何保证消息不丢失？

  • 生产者：Confirm + Return 确认
  • MQ：持久化（交换机/队列/消息）+ LazyQueue
  • 消费者：ACK 确认 + 失败重试 + error 队列

💡 如何保证消息不重复消费（幂等）？

  • 业务判断（先查状态，已处理则跳过）
  • 唯一消息 ID + Redis 去重

💡 延迟消息实现方案？

  • 方案一：TTL + 死信队列（无法按消息设置延迟）
  • 方案二：DelayExchange 插件（推荐，可按消息设置延迟）

💡 消息堆积怎么办？

  • 配置 LazyQueue（消息直接存磁盘）
  • 增加消费者数量（扩容）
  • 增大 prefetch 数量

💡 死信队列的三种触发场景？

  1. 消费者 NACK/REJECT（requeue=false）
  2. 消息 TTL 过期
  3. 队列长度超限

✅ 已掌握：

  • 消息丢失三大环节与解决方案
  • 生产者重试 + 生产者确认（Confirm/Return）
  • 数据持久化 + LazyQueue
  • 消费者 ACK 机制（auto 模式）
  • 失败重试 + RepublishMessageRecoverer
  • 业务幂等性（优先业务判断）
  • 延迟消息：TTL 死信 vs DelayExchange 插件

✅ 易错点：

  • 生产者确认消耗性能，非必要不开
  • LazyQueue 在 3.12+ 已是默认，低版本要手动设置
  • 延迟消息要安装 rabbitmq_delayed_message_exchange 插件
  • 消息重试后仍失败需要投递到 error 队列人工处理
