二、短信登录 ⭐⭐

2.1 Session 的问题

多实例部署时，Session 不共享：

text
用户 → 实例A（写入 Session）
      → 实例B（找不到 Session）❌

2.2 Redis 代替 Session 的设计

text
发送验证码：
  手机号 → 生成验证码 → 存 Redis（key=login:code:手机号，TTL=2分钟）

登录验证：
  手机号+验证码 → 校验 Redis 中的验证码
  → 查询/创建用户 → 生成 token（UUID）
  → 存 Redis（key=login:token:xxx，value=用户信息，TTL=30分钟）
  → 返回 token 给前端

请求拦截：
  请求头携带 token → 拦截器查 Redis → 刷新 TTL → 放行

2.3 Key 设计原则

java
// 验证码 key
"login:code:" + phone        // 2分钟过期

// 登录 token key
"login:token:" + token       // 30分钟过期，每次请求刷新

2.4 登录拦截器

java
public class LoginInterceptor implements HandlerInterceptor {
    private StringRedisTemplate redisTemplate;

    @Override
    public boolean preHandle(HttpServletRequest request,
                              HttpServletResponse response, Object handler) {
        String token = request.getHeader("authorization");
        if (StrUtil.isBlank(token)) {
            response.setStatus(401);
            return false;
        }

        // 从 Redis 查用户
        String key = "login:token:" + token;
        Map<Object, Object> userMap = redisTemplate.opsForHash().entries(key);
        if (userMap.isEmpty()) {
            response.setStatus(401);
            return false;
        }

        // 刷新 TTL
        redisTemplate.expire(key, 30, TimeUnit.MINUTES);

        // 存入 ThreadLocal
        UserHolder.saveUser(BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false));
        return true;
    }
}

三、商户查询缓存 ⭐⭐⭐⭐

3.1 缓存更新策略 ⭐⭐

策略 一致性 维护成本
内存淘汰 差 低
超时剔除 一般 低
主动更新 好 高

主动更新三种方案：

  1. Cache Aside（旁路缓存）：自己维护（推荐）
  2. Write Through：缓存代理写 DB
  3. Write Behind：先写缓存，异步写 DB

Cache Aside 操作顺序（重要！）

读：先查缓存，命中返回；未命中查 DB，写缓存后返回。

写：先操作 DB，再删除缓存（不更新！）。

⚠ 为什么是先删 DB 再删缓存？ 若先删缓存，另一线程读取 → 查 DB → 写旧数据进缓存 → 再删缓存 → 数据不一致。 先操作 DB，再删缓存，出现不一致的概率极低（需 DB 操作和缓存读同时发生）。

3.2 缓存三大问题 ⭐⭐⭐⭐⭐

缓存穿透

问题：请求一个不存在的 key，每次都打到 DB。

解决方案：

方案 原理 优缺点
缓存空值 不存在也缓存 null（短过期时间） 简单，但占内存、可能不一致
布隆过滤器 预先加载存在的 key，请求先过布隆 内存小，但有误判率
java
public Shop queryById(Long id) {
    String key = "cache:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);

    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, Shop.class);  // 命中
    }

    // 命中空值（防穿透）
    if (json != null) return null;

    // 查 DB
    Shop shop = shopMapper.selectById(id);
    if (shop == null) {
        // 缓存空值，2 分钟过期
        stringRedisTemplate.opsForValue().set(key, "", 2, TimeUnit.MINUTES);
        return null;
    }

    stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), 30, TimeUnit.MINUTES);
    return shop;
}

缓存雪崩

问题：大量 key 同时过期 或 Redis 宕机，大量请求打到 DB。

解决方案：

  • 给 key 设置随机 TTL（30分钟 + 随机0~5分钟）
  • Redis 集群（主从 + 哨兵）
  • 降级限流（Sentinel）
  • 多级缓存（本地缓存 + Redis）
java
// 随机 TTL 防雪崩
int ttl = 30 + RandomUtil.randomInt(0, 5);
redisTemplate.opsForValue().set(key, json, ttl, TimeUnit.MINUTES);

缓存击穿

问题：热点 key 过期的瞬间，大量请求同时打到 DB。

方案一：互斥锁（强一致性）

java
public Shop queryById(Long id) {
    String key = "cache:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, Shop.class);
    }
    if (json != null) return null;  // 空值

    // 获取互斥锁
    String lockKey = "lock:shop:" + id;
    Shop shop = null;
    try {
        boolean isLock = tryLock(lockKey);
        if (!isLock) {
            Thread.sleep(50);
            return queryById(id);  // 递归重试
        }
        // 再次检查缓存（DoubleCheck）
        json = stringRedisTemplate.opsForValue().get(key);
        if (StrUtil.isNotBlank(json)) {
            return JSONUtil.toBean(json, Shop.class);
        }
        // 查 DB
        shop = shopMapper.selectById(id);
        if (shop == null) {
            stringRedisTemplate.opsForValue().set(key, "", 2, TimeUnit.MINUTES);
            return null;
        }
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), 30, TimeUnit.MINUTES);
    } catch (Exception e) {
        throw new RuntimeException(e);
    } finally {
        unlock(lockKey);  // 释放锁
    }
    return shop;
}

private boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
    return BooleanUtil.isTrue(flag);
}

private void unlock(String key) {
    stringRedisTemplate.delete(key);
}

方案二：逻辑过期（高可用性）

java
// 存入时带逻辑过期时间（key 本身不设 TTL）
public void setWithLogicalExpire(String key, Object value, Long time, TimeUnit unit) {
    RedisData redisData = new RedisData();
    redisData.setData(value);
    redisData.setExpireTime(LocalDateTime.now().plusSeconds(unit.toSeconds(time)));
    stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(redisData));
}

// 查询时判断逻辑过期
private static final ExecutorService REBUILD_EXECUTOR = Executors.newFixedThreadPool(10);

public Shop queryWithLogicalExpire(Long id) {
    String key = "cache:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);
    if (StrUtil.isBlank(json)) return null;

    RedisData redisData = JSONUtil.toBean(json, RedisData.class);
    Shop shop = JSONUtil.toBean((JSONObject) redisData.getData(), Shop.class);

    if (redisData.getExpireTime().isAfter(LocalDateTime.now())) {
        return shop;  // 未过期，直接返回
    }

    // 已过期，尝试异步重建
    String lockKey = "lock:shop:" + id;
    if (tryLock(lockKey)) {
        REBUILD_EXECUTOR.submit(() -> {
            try {
                Shop newShop = shopMapper.selectById(id);
                setWithLogicalExpire(key, newShop, 30L, TimeUnit.MINUTES);
            } finally {
                unlock(lockKey);
            }
        });
    }
    return shop;  // 返回旧数据（不阻塞）
}

两种方案对比：

互斥锁 逻辑过期
一致性 强一致 弱一致（短暂旧数据）
可用性 低（等待锁） 高（立即返回旧数据）
适合场景 数据要求精确 高并发、可容忍短暂不一致

四、秒杀设计 ⭐⭐⭐⭐

4.1 全局唯一 ID

要求：唯一性、单调递增、高性能、安全性

java
@Component
public class RedisIdWorker {
    private static final long BEGIN_TIMESTAMP = 1640995200L;  // 2022-01-01

    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    public long nextId(String keyPrefix) {
        // 1. 时间戳（31位）
        LocalDateTime now = LocalDateTime.now();
        long nowSecond = now.toEpochSecond(ZoneOffset.UTC);
        long timestamp = nowSecond - BEGIN_TIMESTAMP;

        // 2. 序列号（32位）：用 Redis 自增
        String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
        long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);

        // 3. 拼接：timestamp(31位) | count(32位)
        return timestamp << 32 | count;
    }
}

4.2 超卖问题（乐观锁）⭐⭐⭐

java
// 乐观锁：CAS（版本号/stock 值判断）
@Update("UPDATE voucher_order SET stock = stock - 1 " +
        "WHERE voucher_id = #{voucherId} AND stock > 0")
int updateStock(Long voucherId);

// 下单时调用，stock > 0 才执行
boolean success = seckillVoucherService.update()
    .setSql("stock = stock - 1")
    .eq("voucher_id", voucherId)
    .gt("stock", 0)  // 乐观锁：当前库存 > 0
    .update();

💡 对比悲观锁（synchronized）：乐观锁无需加锁，性能更好，适合写少读多。

4.3 一人一单（分布式锁）⭐⭐

单机无法保证：synchronized 只能锁当前 JVM，分布式下无效。

java
// 错误的做法（集群下无效）
synchronized (userId.toString().intern()) {
    // 下单
}

// 正确：分布式锁
RLock lock = redissonClient.getLock("lock:order:" + userId);
boolean success = lock.tryLock(1, 10, TimeUnit.SECONDS);
if (!success) {
    return Result.fail("不允许重复下单！");
}
try {
    // 下单业务
} finally {
    lock.unlock();
}

五、分布式锁 ⭐⭐⭐⭐⭐

5.1 自实现（SETNX）

java
// 加锁
Boolean success = stringRedisTemplate.opsForValue()
    .setIfAbsent("lock:key", threadId, 10, TimeUnit.SECONDS);

// 释放锁（Lua 保证原子性）
String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                "return redis.call('del', KEYS[1]) else return 0 end";
stringRedisTemplate.execute(
    new DefaultRedisScript<>(script, Long.class),
    Collections.singletonList(lockKey),
    threadId
);

核心问题：

  • 不可重入：同一线程不能多次获取同一把锁
  • 不可续期：业务超时后锁被释放
  • 超时误删：判断 + 删除不原子（Lua 解决）

5.2 Redisson（推荐）⭐⭐⭐

依赖：

xml
<dependency>
    <groupId>org.redisson</groupId>
    <artifactId>redisson-spring-boot-starter</artifactId>
    <version>3.13.6</version>
</dependency>

配置：

java
@Bean
public RedissonClient redissonClient() {
    Config config = new Config();
    config.useSingleServer()
        .setAddress("redis://192.168.150.101:6379")
        .setPassword("123321");
    return Redisson.create(config);
}

使用：

java
RLock lock = redissonClient.getLock("lock:order:" + userId);
boolean isLock = lock.tryLock(1, 10, TimeUnit.SECONDS);
// tryLock(等待时间, 锁超时时间, 时间单位)

if (!isLock) {
    return Result.fail("请勿重复下单");
}
try {
    // 业务逻辑
} finally {
    lock.unlock();
}

Redisson 核心机制：

  • 可重入：Lua 脚本 + Hash 存锁次数
  • WatchDog（看门狗）：后台线程每 10s 自动续期，防止超时
  • 联锁（MultiLock）：在多个 Redis 实例上加锁，防单点故障

六、秒杀优化（异步）⭐⭐⭐

6.1 传统同步秒杀的问题

下单流程在同一个线程中串行执行：

  1. 查库存（DB）
  2. 判断一人一单（DB）
  3. 扣减库存（DB）
  4. 创建订单（DB）

性能差，大量请求阻塞。

6.2 Redis 预校验 + 异步下单

text
请求进来
  ↓
Redis 预校验（纯内存，极快）：
  1. 查库存（Lua 脚本保证原子性）
  2. 判断一人一单
  3. 扣减库存
  ↓
校验通过：生成订单 ID，推到 Stream 消息队列，立即返回
  ↓
异步消费（另一线程）：从 Stream 读取，真正写 DB
java
// Lua 脚本（原子性保证）
String script = "local voucherId = ARGV[1]\n" +
    "local userId = ARGV[2]\n" +
    "local orderId = ARGV[3]\n" +
    "local stockKey = 'seckill:stock:' .. voucherId\n" +
    "local orderKey = 'seckill:order:' .. voucherId\n" +
    "if tonumber(redis.call('get', stockKey)) <= 0 then return 1 end\n" +
    "if redis.call('sismember', orderKey, userId) == 1 then return 2 end\n" +
    "redis.call('incrby', stockKey, -1)\n" +
    "redis.call('sadd', orderKey, userId)\n" +
    "redis.call('xadd', 'stream.orders', '*', 'userId', userId, " +
    "'voucherId', voucherId, 'id', orderId)\n" +
    "return 0";

七、高级数据类型 ⭐⭐

7.1 GEO（地理坐标）

bash
GEOADD key 经度 纬度 member   # 添加
GEODIST key m1 m2 km          # 求距离
GEOPOS key member             # 查坐标
GEOSEARCH key FROMMEMBER m BYRADIUS 5 km ASC COUNT 10  # 附近搜索

使用场景：附近的商家、骑手定位

7.2 BitMap（位图）

bash
SETBIT key offset 0/1    # 设置位
GETBIT key offset         # 获取位
BITCOUNT key              # 统计 1 的数量

使用场景：用户签到（365 天只用 46 字节）

7.3 HyperLogLog（UV 统计）

bash
PFADD key element...      # 添加元素
PFCOUNT key               # 统计基数（有 0.81% 误差）
PFMERGE dest k1 k2        # 合并

使用场景：UV 统计（百万级去重计数，只用 12KB 内存）

八、缓存三大问题总结 ⭐⭐⭐

问题 场景 解决方案
缓存穿透 查不存在的数据 缓存空值 / 布隆过滤器
缓存雪崩 大量 key 同时过期 随机 TTL / 集群 / 降级
缓存击穿 热点 key 过期 互斥锁（强一致）/ 逻辑过期（高可用）

九、面试常问 ⭐⭐⭐

💡 缓存穿透、雪崩、击穿的区别？

  • 穿透：key 不存在，穿透缓存打 DB
  • 雪崩：大量 key 同时过期
  • 击穿：热点 key 过期，瞬间大量请求打 DB

💡 Cache Aside 写操作为什么先删缓存再操作 DB？ 不是！应该先操作 DB，再删除缓存。若先删缓存，可能发生缓存击穿导致缓存写入旧数据。

💡 Redis 分布式锁有什么问题？如何解决？

  • 超时误删：Lua 脚本保证判断+删除原子性
  • 不可重入：Redisson 用 Hash 存重入次数
  • 不可续期：Redisson WatchDog 自动续期

💡 超卖问题怎么解决？ 乐观锁：WHERE stock > 0，不用加锁，CAS 操作。

💡 秒杀怎么优化？ Redis 预校验（Lua 原子操作）+ Stream 消息队列异步下单
