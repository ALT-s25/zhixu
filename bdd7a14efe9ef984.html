二、持久化 ⭐⭐⭐

2.1 RDB（Redis Database）

原理：把内存中的数据以快照方式写入磁盘，生成 .rdb 文件。

bash
# 触发时机
save           # 主进程（阻塞！）
bgsave          # 后台子进程（推荐）
shutdown save   # 关闭时自动触发

bgsave 原理（fork + COW）：

text
主进程
  ↓ fork()
子进程（复制页表）
  ↓ 写入 .rdb
子进程结束，替换旧 rdb
  • fork：创建子进程（极快，共享页表）
  • COW（写时复制）：主进程修改数据时，复制该页数据，不影响子进程读取快照
yaml
# redis.conf RDB 配置
save 900 1      # 900秒内至少1次写入，触发 bgsave
save 300 10
save 60 10000
dbfilename dump.rdb
dir /data/redis

优缺点：

优点 缺点
文件小，恢复快 两次快照间的数据可能丢失
fork 子进程，主进程不阻塞 fork 大数据时耗时久

2.2 AOF（Append Only File）

原理：记录每条写命令到文件，重启时重放恢复数据。

yaml
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec   # always(每次)|everysec(每秒)|no(OS决定)
appendfsync 安全性 性能
always 最高（不丢数据） 最差
everysec 高（最多丢1秒） 折中（推荐）
no 低 最好

AOF 重写（防文件膨胀）：

bash
bgrewriteaof   # 手动触发重写

# 自动触发配置
auto-aof-rewrite-min-size 64mb
auto-aof-rewrite-percentage 100  # 比上次翻倍时触发

2.3 RDB vs AOF 对比 ⭐⭐

RDB AOF
持久化方式 定时快照 追加日志
数据完整性 低（快照间可能丢失） 高（everysec 最多丢1秒）
文件大小 小（二进制压缩） 大（文本命令）
恢复速度 快 慢（需重放）
CPU 影响 fork 时有压力 轻微
推荐 灾备 生产推荐

💡 生产推荐 AOF + RDB 双开：AOF 保数据，RDB 快速恢复。

三、主从架构 ⭐⭐

作用：读写分离（写主读从）+ 数据备份。

3.1 全量同步（首次）

text
Slave → Replica ID（psync ? -1） → Master
Master → fork → bgsave 生成 RDB
Master → 发送 RDB + repl_backlog（期间的写命令）
Slave → 清空数据，加载 RDB + 追加 repl_backlog

3.2 增量同步（断线重连）

text
Slave → psync replId offset → Master
Master → 判断 repl_backlog 中 offset 之后的数据
Master → 发送增量数据

⚠ repl_backlog 是环形缓冲区，默认 1MB。若 Slave 断线太久导致 offset 被覆盖，只能全量同步。

3.3 配置

yaml
# slave 的 redis.conf
replicaof 192.168.150.101 6379   # 主节点地址
replica-read-only yes             # 从节点只读

四、哨兵集群 ⭐⭐⭐

4.1 作用

  • 监控：每秒 PING 主从节点，检测健康状态
  • 自动故障恢复：主节点宕机后自动推选新主节点
  • 通知：通知客户端新主节点地址

4.2 故障恢复流程

text
1. Sentinel 发现 master 无响应（subjectively down）
2. 超过半数 Sentinel 确认（objectively down）
3. 投票选出 Leader Sentinel
4. Leader 选出新 Master（优先级 → 复制进度 → runId）
5. 通知其他 Slave 追随新 Master（REPLICAOF）
6. 通知客户端（订阅频道）

4.3 SpringDataRedis 配置哨兵

yaml
spring:
  redis:
    sentinel:
      master: mymaster
      nodes:
        - 192.168.150.101:27001
        - 192.168.150.101:27002
        - 192.168.150.101:27003
    password: 123321

# 读写分离
@Bean
public LettuceClientConfigurationBuilderCustomizer customizer() {
    return builder -> builder.readFrom(ReadFrom.REPLICA_PREFERRED);
    // REPLICA_PREFERRED：优先从从节点读，不可用才读主节点
}

五、分片集群 ⭐⭐⭐

解决：单机内存不足（水平扩展）。

5.1 散列插槽（Hash Slot）

  • Redis 集群有 16384 个插槽（slot 0 ~ 16383）
  • key 经过 CRC16(key) % 16384 计算得到插槽编号
  • 每个 master 节点负责一部分插槽
bash
# 计算 key 的插槽
cluster keyslot key

💡 {} 控制插槽：{user}:1 和 {user}:2 属于同一插槽（只计算 {} 内的部分），方便事务。

5.2 结构

text
3 个 Master：
  master1（slot 0~5460）→ slave1
  master2（slot 5461~10922）→ slave2
  master3（slot 10923~16383）→ slave3

5.3 故障转移

  • 自动：slave 升为 master（投票）
  • 手动：cluster failover（优雅切换，等待同步完成）

六、底层数据结构（原理）⭐⭐

6.1 SDS（简单动态字符串）

Redis 的字符串不用 C 的 char*，而是自定义 SDS：

c
struct SDS {
    int len;     // 已用长度
    int alloc;   // 总分配长度
    char buf[];  // 字符数组
};

优点：

  • O(1) 获取长度
  • 预分配空间，减少扩容次数
  • 二进制安全（不以 \0 结尾）

6.2 Dict（哈希表）

  • 底层是两个 hashTable（ht[0] 和 ht[1]）
  • 渐进式 rehash：扩容时不一次性迁移，每次操作迁移一部分

6.3 ZipList（压缩链表）

紧凑存储，entry 连续在内存中，每个 entry 记录前一个 entry 长度（prevlen）。

连锁更新问题：一个 entry 长度变化 → prevlen 大小变化 → 触发后续 entry 更新（级联）。

6.4 QuickList

LinkedList（双向链表） + ZipList（节点存储）：

text
QuickList
  ↓ 节点1（ZipList）→ 节点2（ZipList）→ ...

每个节点是 ZipList，限制 ZipList 大小（默认 128 个元素或 64 字节），避免连锁更新。

6.5 RedisObject

每个 value 都是 RedisObject：

c
struct RedisObject {
    unsigned type:4;      // 对外类型（String/Hash/List...）
    unsigned encoding:4;  // 底层编码
    unsigned lru:24;      // 最近访问时间（内存淘汰用）
    int refcount;          // 引用计数
    void *ptr;             // 指向数据
};

各类型编码方式：

外部类型 内部编码 条件
String int 整数且范围内
String embstr ≤ 44 字节
String raw > 44 字节
Hash ziplist 元素少且值短
Hash hashtable 元素多或值长
List quicklist 任何情况
Set intset 纯整数且少量
Set hashtable 其他
ZSet ziplist 元素少且值短
ZSet skiplist + hashtable 元素多或值长

七、网络模型 ⭐⭐⭐

7.1 IO 多路复用

问题：Redis 单线程如何同时处理数千个连接？

IO 多路复用（epoll）：

  • 一个线程监控多个 socket
  • 哪个 socket 有数据可读/写，通知主线程处理
text
epoll_create → 创建 epoll 实例
epoll_ctl    → 注册 socket
epoll_wait   → 阻塞等待，返回就绪的 socket 列表
read/write   → 只处理就绪的 socket

ET vs LT：

  • LT（水平触发）：只要有数据就一直通知（默认）
  • ET（边缘触发）：数据就绪时只通知一次，需一次性读完

7.2 Redis 单线程模型

text
主线程
  ↓
IO 多路复用（epoll）监听多个 socket
  ↓
事件队列（读/写/连接/断开）
  ↓
事件处理（命令执行）
  ↓
响应

Redis 是单线程的吗？

  • 命令执行：单线程（保证原子性）
  • IO 处理（Redis 6.0+）：多线程（读写分离）
  • 持久化、主从同步：后台线程

八、内存管理 ⭐⭐⭐

8.1 过期 key 处理

两种策略结合使用：

策略 原理 优缺点
惰性删除 访问时才检查是否过期 节省 CPU，可能浪费内存
定期删除 定时扫描部分 key，删过期的 两者折中
text
定期删除：每次扫描 20 个随机 key，删除过期的
若比例 > 25%，立即再扫一轮（循环）

8.2 内存淘汰策略 ⭐⭐⭐（面试高频）

当内存达到 maxmemory 时，触发淘汰：

策略 说明
noeviction 不淘汰，新写入直接报错（默认）
allkeys-lru 所有 key 中淘汰最久未使用的（推荐）
volatile-lru 有 TTL 的 key 中淘汰最久未使用的
allkeys-random 随机淘汰
volatile-random 有 TTL 的随机淘汰
volatile-ttl TTL 最短的先淘汰
allkeys-lfu 所有 key 中淘汰访问频率最低的
volatile-lfu 有 TTL 的 key 中淘汰访问频率最低的
yaml
maxmemory 1gb
maxmemory-policy allkeys-lru   # 推荐

💡 LRU（最近最少使用）vs LFU（最不经常使用）

  • LRU：删最久没访问的
  • LFU：删访问次数最少的（更精准）

九、面试常问 ⭐⭐⭐

💡 RDB 和 AOF 的区别？

  • RDB 定时快照，文件小、恢复快，但可能丢数据
  • AOF 追加日志，数据安全（everysec 最多丢1秒），但文件大、恢复慢
  • 生产推荐两者结合：RDB 用于快速恢复，AOF 保证数据安全

💡 主从同步原理？ 首次全量同步：RDB + repl_backlog；断线重连增量同步：通过 offset 续传

💡 哨兵和集群的区别？

  • 哨兵：监控主从，主节点故障自动切换（高可用）
  • 分片集群：数据分散在多个 master（高容量 + 高可用）

💡 Redis 为什么是单线程？ 命令执行单线程保证原子性。内存操作极快，瓶颈在网络 IO 而非 CPU，单线程足够。

💡 内存淘汰策略有哪些？推荐用哪个？ 8 种，推荐 allkeys-lru（全量 LRU）。如果 key 有热冷区分，用 allkeys-lfu 更精准。

💡 Redis 过期 key 是怎么删除的？ 惰性删除（访问时检查）+ 定期删除（定时扫描 20 个随机 key）。
