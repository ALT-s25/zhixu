一、什么是索引

1.1 生活类比：书的目录

假设你有一本 1000 页的《MySQL 技术内幕》，你想找"InnoDB 锁机制"这个章节。

没有目录： 你只能从第 1 页翻到第 1000 页，直到找到为止 → 全表扫描

有目录： 你翻到目录页，查到"InnoDB 锁机制"在第 523 页，直接翻到 523 页 → 索引查找

索引就是数据库的"目录"，让查询不用遍历所有数据，直接定位到目标行。

1.2 索引的本质

索引是一种数据结构，存储了某列（或多列）的值及其对应数据行的物理位置（主键或行地址）。

有索引 vs 无索引：

  • 无索引：SELECT * FROM users WHERE name='张三' → 扫描全部 100 万行
  • 有索引：MySQL 通过 B+ 树直接定位到"张三"所在的 1~2 行 → 极快

代价：

  • 索引占用额外磁盘空间
  • 写操作（INSERT/UPDATE/DELETE）需要维护索引，略有性能损耗
  • 因此，不是索引越多越好

二、索引的分类

2.1 主键索引（PRIMARY KEY）

表的主键自动创建主键索引，是最重要、最高效的索引。

sql
-- 创建表时指定主键（自动创建主键索引）
CREATE TABLE users (
    id       INT PRIMARY KEY AUTO_INCREMENT,  -- 主键，自动创建索引
    username VARCHAR(50),
    age      INT
);

-- 也可以单独定义
CREATE TABLE users (
    id       INT AUTO_INCREMENT,
    username VARCHAR(50),
    PRIMARY KEY (id)  -- 明确指定主键
);

特点：

  • 一张表只能有一个主键索引
  • 主键值必须唯一且不能为 NULL
  • InnoDB 表按主键顺序存储数据（聚簇索引）

2.2 唯一索引（UNIQUE INDEX）

保证列中所有值都唯一，允许有 NULL（但只能有一个 NULL）。

sql
-- 创建时添加唯一索引
CREATE TABLE users (
    id       INT PRIMARY KEY AUTO_INCREMENT,
    email    VARCHAR(100) UNIQUE,       -- 写法1：列定义时
    phone    VARCHAR(20),
    UNIQUE INDEX idx_phone (phone)      -- 写法2：单独定义
);

-- 已有表，添加唯一索引
ALTER TABLE users ADD UNIQUE INDEX idx_email (email);

使用场景： 邮箱、手机号、身份证号等需要唯一的字段。

2.3 普通索引（INDEX）

最基本的索引类型，没有唯一性约束，单纯为了加速查询。

sql
-- 创建时添加普通索引
CREATE TABLE articles (
    id         INT PRIMARY KEY AUTO_INCREMENT,
    title      VARCHAR(200),
    author_id  INT,
    created_at DATETIME,
    INDEX idx_author (author_id),      -- 普通索引
    INDEX idx_created (created_at)     -- 时间索引
);

-- 已有表，添加普通索引
ALTER TABLE articles ADD INDEX idx_author (author_id);
-- 或
CREATE INDEX idx_author ON articles (author_id);

使用场景： 经常出现在 WHERE、JOIN、ORDER BY 子句中的字段。

2.4 全文索引（FULLTEXT）

用于全文搜索，支持对文本内容进行关键词搜索，比 LIKE 高效得多。

sql
-- 创建全文索引
CREATE TABLE articles (
    id      INT PRIMARY KEY AUTO_INCREMENT,
    title   VARCHAR(200),
    content TEXT,
    FULLTEXT INDEX ft_content (content)  -- 全文索引
);

-- 使用全文索引搜索（MATCH...AGAINST 语法）
SELECT * FROM articles 
WHERE MATCH(content) AGAINST('MySQL 事务' IN BOOLEAN MODE);
-- IN BOOLEAN MODE：支持 +词（必须包含）、-词（必须排除）

注意： 中文全文搜索需要使用 ngram 解析器，或者考虑使用 Elasticsearch。

2.5 组合索引（Composite Index）

在多个列上创建的索引，遵循最左前缀原则（见第五节）。

sql
-- 创建组合索引
CREATE TABLE orders (
    id       INT PRIMARY KEY AUTO_INCREMENT,
    user_id  INT,
    status   TINYINT,
    amount   DECIMAL(10,2),
    -- 组合索引：user_id 和 status 两列
    INDEX idx_user_status (user_id, status)
);

-- 能用到 idx_user_status 的查询：
SELECT * FROM orders WHERE user_id=1;                     -- ✅ 用到
SELECT * FROM orders WHERE user_id=1 AND status=2;        -- ✅ 用到
-- 不能用到的查询：
SELECT * FROM orders WHERE status=2;                      -- ❌ 不用（违反最左前缀）

三、索引底层结构：B+ 树

3.1 B+ 树是什么

B+ 树（B-Plus Tree）是索引的核心数据结构。理解它才能真正理解索引的原理。

B+ 树结构特点：

  1. 多叉树： 每个节点可以有多个子节点（比二叉树矮，层数少，IO 少）
  2. 所有数据在叶子节点： 非叶子节点只存索引（键值），不存实际数据
  3. 叶子节点链表： 所有叶子节点通过链表相连，支持范围查询
  4. 有序： 叶子节点中的数据按键值有序排列
text
                    B+ 树示意图

               [10 | 30 | 50]           ← 根节点（非叶子，只存键）
              /    |    |    \
     [1|5|9] [12|20] [32|40] [55|70]   ← 中间节点
        |       |       |       |
    [1][5][9]-[12][20]-[32][40]-[55][70]  ← 叶子节点（存实际数据，链表相连）

3.2 为什么用 B+ 树，而不用哈希表？

对比维度 B+ 树 哈希表
等值查询 O(log n) O(1) ✅ 更快
范围查询 O(log n + k) ✅ 支持 ❌ 不支持
排序（ORDER BY） ✅ 天然有序 ❌ 不支持
LIKE 前缀查询 ✅ 支持 ❌ 不支持
存储效率 较高 高（但有哈希冲突）

结论： 哈希表等值查询很快，但不支持范围查询、排序、前缀查询。数据库中这些操作非常常见，所以 B+ 树更适合作为索引结构。

MySQL 的 Memory 引擎支持哈希索引，但 InnoDB（最常用的引擎）默认使用 B+ 树。

3.3 聚簇索引 vs 非聚簇索引

text
聚簇索引（主键索引）：
叶子节点存储的是实际数据行
     [主键] → [整行数据]
     好处：通过主键查询，一次就能拿到数据

非聚簇索引（二级索引/辅助索引）：
叶子节点存储的是主键值
     [索引列值] → [主键值]
     需要回表：先查到主键，再通过主键查整行数据

回表（Back to Table）： 使用非主键索引查询时，先在二级索引找到主键，再用主键去聚簇索引找整行数据，这个过程叫回表。回表有额外开销，所以覆盖索引（见面试题）可以避免回表。

四、索引操作

4.1 创建索引

sql
-- ===== 方式1：CREATE TABLE 时创建 =====
CREATE TABLE employees (
    id         INT PRIMARY KEY AUTO_INCREMENT,
    name       VARCHAR(50),
    dept_id    INT,
    hire_date  DATE,
    salary     DECIMAL(10,2),
    -- 普通索引
    INDEX idx_dept (dept_id),
    -- 组合索引
    INDEX idx_dept_hire (dept_id, hire_date)
);

-- ===== 方式2：ALTER TABLE 添加索引 =====
ALTER TABLE employees ADD INDEX idx_name (name);
ALTER TABLE employees ADD UNIQUE INDEX idx_name_unique (name);

-- ===== 方式3：CREATE INDEX 语句 =====
CREATE INDEX idx_salary ON employees (salary);
CREATE UNIQUE INDEX idx_name ON employees (name);

4.2 查看索引

sql
-- 查看表的所有索引
SHOW INDEX FROM employees;
-- 返回字段：Table/Key_name/Column_name/Non_unique/Seq_in_index 等

-- 也可以用 SHOW CREATE TABLE 查看
SHOW CREATE TABLE employees;

4.3 删除索引

sql
-- 方式1：DROP INDEX
DROP INDEX idx_name ON employees;

-- 方式2：ALTER TABLE
ALTER TABLE employees DROP INDEX idx_dept;

-- 删除主键索引（特殊）
ALTER TABLE employees DROP PRIMARY KEY;
-- 注意：删除主键前需要先去掉 AUTO_INCREMENT，否则报错

五、最左前缀原则（组合索引必看）

5.1 什么是最左前缀原则

使用组合索引时，查询条件必须从索引的最左边列开始，不能跳过中间列。

sql
-- 假设有组合索引：INDEX idx_a_b_c (a, b, c)
-- 可以把这个索引想象成电话簿：先按姓排序，再按名排序，再按生日排序

-- ✅ 能用到索引
SELECT * FROM t WHERE a=1;              -- 用到 a
SELECT * FROM t WHERE a=1 AND b=2;      -- 用到 a, b
SELECT * FROM t WHERE a=1 AND b=2 AND c=3; -- 用到 a, b, c
SELECT * FROM t WHERE a=1 AND c=3;      -- 用到 a（c 跳过了 b，c 不走索引）

-- ❌ 不能用到索引（没有从最左列开始）
SELECT * FROM t WHERE b=2;              -- 不走索引
SELECT * FROM t WHERE c=3;              -- 不走索引
SELECT * FROM t WHERE b=2 AND c=3;      -- 不走索引

5.2 生活类比：字典排序

字典里的词是先按第一个字母排序，再按第二个字母排序...

  • 你想找"apple"：先找"a"，再找"ap"，再找"app"... ✅（从头开始，能用索引）
  • 你想找所有以"le"结尾的词：没法用字典顺序找... ❌（不从头开始，不走索引）

5.3 范围查询对后续列的影响

sql
-- 假设索引：INDEX idx_a_b_c (a, b, c)

-- a 是范围查询时，b 和 c 无法走索引
SELECT * FROM t WHERE a > 1 AND b = 2;
-- a 走了范围查询，b 不能走索引

-- 解决方案：把等值查询列放在前面
-- 建索引时：INDEX idx_b_a (b, a)  把 b 放前面
SELECT * FROM t WHERE b=2 AND a>1;  -- b 走索引，a 也能部分走索引

六、索引失效的 8 种常见情况

重点！面试必考！

情况1：LIKE 以通配符开头

sql
-- ❌ 索引失效（% 在开头，无法确定从哪里开始查）
SELECT * FROM users WHERE name LIKE '%张%';
SELECT * FROM users WHERE name LIKE '%张';

-- ✅ 有效（% 在末尾，可以从头开始匹配）
SELECT * FROM users WHERE name LIKE '张%';

原因： B+ 树是按前缀排序的，%张% 无法从树根开始按序查找。

情况2：对索引列使用函数

sql
-- ❌ 索引失效（对索引列 created_at 使用了函数）
SELECT * FROM orders WHERE YEAR(created_at) = 2024;
SELECT * FROM orders WHERE DATE_FORMAT(created_at, '%Y') = '2024';

-- ✅ 改写为范围查询
SELECT * FROM orders 
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';

原因： MySQL 无法预知函数的结果，必须对每行计算，只能全表扫描。

情况3：对索引列做数学运算

sql
-- ❌ 索引失效（对索引列 id 做了运算）
SELECT * FROM users WHERE id + 1 = 100;
SELECT * FROM products WHERE price * 1.1 > 1000;

-- ✅ 把运算移到等号右边
SELECT * FROM users WHERE id = 99;
SELECT * FROM products WHERE price > 1000 / 1.1;

情况4：隐式类型转换

sql
-- 假设 phone 字段是 VARCHAR 类型，且有索引

-- ❌ 索引失效（传入的是数字 13800138000，VARCHAR 和 INT 类型不匹配）
SELECT * FROM users WHERE phone = 13800138000;
-- MySQL 会对 phone 列做隐式转换：CAST(phone AS INT)，导致索引失效

-- ✅ 传字符串
SELECT * FROM users WHERE phone = '13800138000';

原因： 类型不一致时，MySQL 对索引列做类型转换，相当于对索引列用了函数。

情况5：OR 连接的条件有非索引列

sql
-- 假设 name 有索引，address 没有索引

-- ❌ 索引失效（OR 中 address 没有索引，MySQL 只能全表扫描）
SELECT * FROM users WHERE name='张三' OR address='北京';

-- ✅ 解决方案1：给 address 也加索引
ALTER TABLE users ADD INDEX idx_address (address);

-- ✅ 解决方案2：用 UNION 代替 OR
SELECT * FROM users WHERE name='张三'
UNION
SELECT * FROM users WHERE address='北京';

情况6：NOT IN / NOT EXISTS

sql
-- ❌ 索引可能失效（NOT IN 有时走不了索引）
SELECT * FROM users WHERE id NOT IN (1, 2, 3);

-- ✅ 改写思路：用 LEFT JOIN 代替 NOT EXISTS
SELECT u.* FROM users u
LEFT JOIN exclude_list e ON u.id = e.user_id
WHERE e.user_id IS NULL;

注意： IN 本身是可以走索引的，NOT IN 要根据数据分布判断。

情况7：索引列参与 IS NULL / IS NOT NULL（视数据分布）

sql
-- 视情况而定（当 NULL 值很多时，MySQL 可能放弃索引）
SELECT * FROM users WHERE deleted_at IS NULL;
-- 如果 90% 的数据 deleted_at 都是 NULL，全表扫描反而更快

-- 建议：尽量设计字段为 NOT NULL，用默认值代替 NULL

情况8：数据量少，MySQL 认为全表扫描更快

sql
-- 即使 name 有索引，MySQL 也可能不走
SELECT * FROM users WHERE name='张三';
-- 如果表只有 10 行，MySQL 优化器会认为全表扫描比走索引更快（减少 IO 次数）
-- 这是正常行为，不用担心

总结口诀： 模糊左开头，函数运算别对列，类型要匹配，OR 有非索引全失效

七、EXPLAIN 执行计划分析

7.1 什么是 EXPLAIN

EXPLAIN 是 MySQL 提供的查询分析工具，可以查看 MySQL 如何执行一条 SQL，是否用到了索引，扫描了多少行。

sql
-- 基本用法：在 SELECT 前加 EXPLAIN
EXPLAIN SELECT * FROM users WHERE name='张三';

7.2 重要字段详解

执行 EXPLAIN 后会返回以下列：

text
+----+-------------+-------+------------+------+---------------+----------+---------+-------+------+----------+-------+
| id | select_type | table | partitions | type | possible_keys | key      | key_len | ref   | rows | filtered | Extra |
+----+-------------+-------+------------+------+---------------+----------+---------+-------+------+----------+-------+

type 字段（最重要！）

type 表示查询的访问类型，性能从好到差排列：

type 值 说明 示例
system 表只有一行（最优） 系统表
const 主键或唯一索引等值查询（极快） WHERE id=1
eq_ref JOIN 时主键或唯一索引匹配 JOIN ON a.id=b.id
ref 非唯一索引等值查询 WHERE name='张三'
range 索引范围查询 WHERE id>10
index 全索引扫描（比全表快） 只查索引列
ALL 全表扫描（最差）⚠️ 无索引条件

目标： type 至少要达到 ref 级别，range 也可以接受，ALL 通常需要优化。

key 字段

sql
-- key：实际使用的索引名称
-- key 为 NULL → 没有用到任何索引 → 需要优化
EXPLAIN SELECT * FROM users WHERE age > 20;
-- 如果 age 没有索引，key 显示 NULL

rows 字段

sql
-- rows：MySQL 预估需要扫描的行数
-- 越小越好，行数很大说明索引效率低或未命中索引
EXPLAIN SELECT * FROM users WHERE name LIKE '%张%';
-- rows 可能等于全表行数，说明走了全表扫描

Extra 字段（重要提示）

Extra 值 含义
Using index ✅ 覆盖索引，无需回表，非常高效
Using where 在存储引擎层之外过滤，可能有优化空间
Using filesort ⚠️ 文件排序，ORDER BY 未走索引，需优化
Using temporary ⚠️ 使用了临时表，GROUP BY/ORDER BY 时出现
Using index condition 索引条件下推（ICP），较好

7.3 EXPLAIN 实战示例

sql
-- 建表和索引
CREATE TABLE employees (
    id       INT PRIMARY KEY AUTO_INCREMENT,
    name     VARCHAR(50),
    dept_id  INT,
    salary   DECIMAL(10,2),
    INDEX idx_dept_salary (dept_id, salary)
);

-- 案例1：走组合索引
EXPLAIN SELECT * FROM employees WHERE dept_id=1 AND salary > 5000;
-- type: range, key: idx_dept_salary ✅

-- 案例2：索引失效
EXPLAIN SELECT * FROM employees WHERE salary > 5000;
-- type: ALL, key: NULL ❌（违反最左前缀，dept_id 没出现）

-- 案例3：覆盖索引（避免回表）
EXPLAIN SELECT dept_id, salary FROM employees WHERE dept_id=1;
-- type: ref, key: idx_dept_salary, Extra: Using index ✅（只查索引列，不回表）

-- 案例4：文件排序（需优化）
EXPLAIN SELECT * FROM employees ORDER BY salary;
-- type: ALL, Extra: Using filesort ❌（salary 单独排序没有索引）

八、慢查询优化思路

8.1 开启慢查询日志

sql
-- 查看慢查询日志配置
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';  -- 默认 10 秒

-- 开启慢查询日志（临时，当前 session）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过 1 秒的查询记录到日志

-- 查看慢查询日志位置
SHOW VARIABLES LIKE 'slow_query_log_file';

8.2 优化思路（五步法）

text
Step 1: 发现慢查询
        → 慢查询日志 / SHOW PROCESSLIST / 监控工具

Step 2: 分析 SQL
        → EXPLAIN 查看执行计划
        → 关注 type / key / rows / Extra

Step 3: 是否命中索引？
        → NO → 添加合适的索引
        → YES → 看索引是否高效（rows 是否很大）

Step 4: 优化 SQL 写法
        → 避免 SELECT *，只查需要的列
        → 避免索引失效的写法
        → 大偏移分页用 WHERE id > 上次最大id 代替 LIMIT offset

Step 5: 考虑业务优化
        → 读多写少 → 加缓存（Redis）
        → 大表 → 分库分表
        → 冷热数据 → 归档

8.3 常见优化手段

sql
-- ===== 1. 只查需要的列，避免 SELECT * =====
-- ❌
SELECT * FROM orders WHERE user_id=1;
-- ✅（如果只需要 id 和 amount）
SELECT id, amount FROM orders WHERE user_id=1;

-- ===== 2. 大偏移分页优化 =====
-- ❌ LIMIT 大偏移极慢（需要扫描 1000000 行后丢弃）
SELECT * FROM orders LIMIT 1000000, 10;
-- ✅ 利用主键索引，从上次查到的最大 id 开始
SELECT * FROM orders WHERE id > 999999 LIMIT 10;

-- ===== 3. 避免 SELECT COUNT(*) 大表全扫描 =====
-- ❌ 大表 COUNT(*) 很慢
SELECT COUNT(*) FROM big_table;
-- ✅ 通过索引列 COUNT（更快）
SELECT COUNT(id) FROM big_table;
-- ✅ 或使用 information_schema（近似值，极快）
SELECT TABLE_ROWS FROM information_schema.TABLES 
WHERE TABLE_NAME='big_table' AND TABLE_SCHEMA='your_db';

-- ===== 4. 利用覆盖索引避免回表 =====
-- 假设有索引 INDEX idx_user_amount (user_id, amount)
-- ❌ 要回表（SELECT * 包含不在索引里的列）
SELECT * FROM orders WHERE user_id=1;
-- ✅ 覆盖索引，不回表
SELECT user_id, amount FROM orders WHERE user_id=1;
-- Extra 显示 Using index，不需要回到主键索引取数据

-- ===== 5. 强制使用指定索引（调试用）=====
SELECT * FROM orders USE INDEX (idx_user_amount) WHERE user_id=1;
SELECT * FROM orders FORCE INDEX (idx_user_amount) WHERE user_id=1;

九、完整代码示例

sql
-- ===== 创建电商订单表，演示索引最佳实践 =====

CREATE TABLE orders (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT, -- 主键，自动有主键索引
    order_no    VARCHAR(32) NOT NULL UNIQUE,       -- 订单号，唯一索引
    user_id     INT NOT NULL,                      -- 用户ID
    status      TINYINT NOT NULL DEFAULT 0,        -- 订单状态：0待付款 1已付款 2已发货 3完成 4取消
    amount      DECIMAL(10,2) NOT NULL,            -- 订单金额
    created_at  DATETIME NOT NULL,                 -- 创建时间
    updated_at  DATETIME,                          -- 更新时间
    remark      TEXT,                              -- 备注（文本，不适合建索引）

    -- 普通索引：按用户查订单
    INDEX idx_user_id (user_id),
    -- 组合索引：按用户+状态查（符合最左前缀）
    INDEX idx_user_status (user_id, status),
    -- 时间索引：按时间范围查
    INDEX idx_created_at (created_at),
    -- 组合索引：用于统计（用户+时间范围+状态）
    INDEX idx_user_created_status (user_id, created_at, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ===== 插入测试数据 =====
INSERT INTO orders (order_no, user_id, status, amount, created_at) VALUES
('ORD20241201001', 1, 3, 299.00, '2024-12-01 10:00:00'),
('ORD20241201002', 1, 1, 599.00, '2024-12-01 11:00:00'),
('ORD20241202001', 2, 0, 1299.00, '2024-12-02 09:00:00'),
('ORD20241202002', 1, 2, 89.00, '2024-12-02 14:00:00'),
('ORD20241203001', 3, 4, 399.00, '2024-12-03 16:00:00');

-- ===== 各种查询场景及索引使用 =====

-- 场景1：按订单号查（唯一索引，type=const）
EXPLAIN SELECT * FROM orders WHERE order_no='ORD20241201001';
-- type: const ✅

-- 场景2：按用户ID查所有订单（普通索引）
EXPLAIN SELECT * FROM orders WHERE user_id=1;
-- type: ref, key: idx_user_id ✅

-- 场景3：按用户+状态查（组合索引完整匹配）
EXPLAIN SELECT * FROM orders WHERE user_id=1 AND status=3;
-- type: ref, key: idx_user_status ✅

-- 场景4：按时间范围查（范围查询）
EXPLAIN SELECT * FROM orders WHERE created_at >= '2024-12-01' AND created_at < '2024-12-03';
-- type: range, key: idx_created_at ✅

-- 场景5：覆盖索引（只查 user_id 和 status）
EXPLAIN SELECT user_id, status FROM orders WHERE user_id=1;
-- type: ref, key: idx_user_id, Extra: Using index ✅

-- 场景6：索引失效演示
EXPLAIN SELECT * FROM orders WHERE YEAR(created_at)=2024;
-- type: ALL, key: NULL ❌（函数导致索引失效）

-- ===== 分页查询最佳实践 =====

-- ❌ 传统分页（第 1000 页，每页 20 条）—— 超慢
SELECT * FROM orders WHERE user_id=1 ORDER BY id LIMIT 19980, 20;

-- ✅ 游标分页（需要客户端传入上一页最后的 id）
SELECT * FROM orders 
WHERE user_id=1 AND id > 19999  -- 上一页最后一条的 id
ORDER BY id 
LIMIT 20;
-- 利用主键索引，直接从 id=19999 之后开始，极快

-- ===== 查看索引统计信息 =====
SHOW INDEX FROM orders;
-- Key_name: 索引名称
-- Cardinality: 索引列的不重复值数量（越大，索引效率越高）
-- Column_name: 索引所在列

十、常见报错

10.1 Duplicate entry（唯一索引冲突）

报错信息：

text
ERROR 1062 (23000): Duplicate entry 'ORD20241201001' for key 'orders.order_no'

原因： 插入或更新的值违反了唯一索引约束。

解决方案：

sql
-- 方案1：INSERT IGNORE（忽略重复，静默失败）
INSERT IGNORE INTO orders (order_no, ...) VALUES ('ORD20241201001', ...);

-- 方案2：ON DUPLICATE KEY UPDATE（冲突时执行更新）
INSERT INTO orders (order_no, amount, ...) 
VALUES ('ORD20241201001', 599.00, ...)
ON DUPLICATE KEY UPDATE amount=599.00;

-- 方案3：先查后插（应用层判断）
SELECT COUNT(*) FROM orders WHERE order_no='ORD20241201001';
-- count=0 才执行 INSERT

10.2 Too many keys（索引数量超限）

报错信息：

text
ERROR 1069 (42000): Too many keys specified; max 64 keys allowed

解决方案： 一张表索引不要超过 5~7 个，检查是否有冗余索引。

10.3 Specified key was too long（索引键太长）

报错信息：

text
ERROR 1071 (42000): Specified key was too long; max key length is 767 bytes

解决方案：

sql
-- 对长文本字段建索引时，指定索引前缀长度
CREATE INDEX idx_name ON users (name(50));  -- 只索引前 50 个字符
-- 或修改 ROW_FORMAT 为 DYNAMIC（InnoDB 支持更长的索引键）

十一、面试常问

Q1：B+ 树和哈希索引的区别？什么情况用哈希？

参考回答：

B+ 树适合大多数场景（等值、范围、排序、前缀查询均支持）；哈希索引只适合等值查询（WHERE key=value），不支持范围查询、排序、LIKE 前缀。

哈希索引适合：内存引擎（MEMORY）、极少范围查询的场景。

实际生产中，InnoDB 使用自适应哈希（Adaptive Hash Index），对频繁访问的索引页自动在内存中建哈希索引加速等值查询，无需手动设置。

Q2：索引失效的常见场景？

参考回答：

  1. LIKE 以 % 开头（%关键词）
  2. 对索引列使用函数（YEAR(date_col)）
  3. 对索引列做数学运算（id+1=100）
  4. 隐式类型转换（字段是 VARCHAR，查询传 INT）
  5. OR 条件中有非索引列
  6. 索引选择性低，MySQL 认为全扫更快
  7. NOT IN / NOT EXISTS（部分情况）
  8. 违反最左前缀原则（组合索引）

Q3：什么是覆盖索引？有什么好处？

参考回答：

覆盖索引（Covering Index）是指查询所需的所有列都包含在索引中，不需要回表。

例如：有索引 INDEX idx(user_id, amount)，执行 SELECT user_id, amount FROM orders WHERE user_id=1 时，只需要访问索引树就能拿到所有数据，不需要回到主键索引（聚簇索引）取整行数据。

好处：

  • 减少一次 IO（避免回表）
  • EXPLAIN 中 Extra 显示 Using index
  • 对读密集型查询性能提升显著

Q4：什么是回表？如何减少回表？

参考回答：

回表是指使用非主键索引查询时，先在二级索引中找到主键值，再用主键值去聚簇索引（主键索引）中取完整行数据的过程，需要两次 B+ 树查询。

减少回表的方法：

  1. 覆盖索引： 把查询需要的列都放入索引，避免回表
  2. 只查需要的列： 不用 SELECT *，减少需要回表的场景
  3. 主键查询： 直接用主键查询天然不需要回表

Q5：联合索引（组合索引）的最左前缀原则是什么？

参考回答：

最左前缀原则是指：使用组合索引时，查询条件必须包含索引定义中最左侧的列，才能用到该索引。

例如索引 (a, b, c)：

  • WHERE a=1 → 走索引（只用 a）
  • WHERE a=1 AND b=2 → 走索引（用 a 和 b）
  • WHERE a=1 AND b=2 AND c=3 → 走索引（全部用到）
  • WHERE b=2 → 不走索引（跳过了 a）
  • WHERE a=1 AND c=3 → a 走索引，c 不走（跳过了 b）

原理：组合索引的 B+ 树按最左列排序，次列在最左列相同时才有序，跳过最左列无法按序查找。

Q6：EXPLAIN 中 type=ALL 是什么意思？如何优化？

参考回答：

type=ALL 表示全表扫描，MySQL 需要遍历每一行数据，是最差的访问类型。

优化方向：

  1. 检查 WHERE 条件中的列是否有索引
  2. 如果是 LIKE '%关键词%' 导致的，改用全文索引或搜索引擎
  3. 检查是否有索引失效的情况（函数、类型不匹配等）
  4. 如果表很小（<几百行），ALL 是正常且合理的
