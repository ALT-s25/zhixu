第一章：为什么要用 MQ（消息队列）

1.1 先讲个故事：外卖下单

你在美团下了一单外卖，整个流程：

同步方式（现实是这样）：

text
你下单 → 餐厅收到 → 厨师做菜 → 骑手接单 → 骑手到店 → 拿餐 → 送到你家

你下完单后，等 30 分钟，外卖才送到。期间你可以去干别的。

如果把"同步"类比到代码：

text
你下单（请求） → 系统依次处理每一步 → 所有步骤完成后 → 返回结果给你

你必须等所有步骤都完成才能收到响应，很慢。

1.2 同步调用的问题（代码角度）

以"用户支付"为例：

text
用户支付 → 1.扣减余额（50ms）
         → 2.更新支付流水（50ms）
         → 3.更新订单状态（50ms）
         → 4.发送短信通知（50ms）
         → 5.给用户发积分（50ms）
         → 返回"支付成功"

总耗时：250ms

这里有三个问题：

问题 1：拓展性差

每次新增功能（比如加返券、加消费记录），都要改支付代码。代码越来越臃肿，违反开闭原则（对扩展开放、对修改关闭）。

问题 2：性能下降

5 个步骤串行执行，250ms 才能返回。用户体验差。

问题 3：级联失败

第 4 步"发短信"失败了，整个事务回滚，用户余额已扣了但订单没更新。

1.3 异步调用：引入 MQ

思路：支付只管"扣余额 + 更新流水"，然后发一条消息告诉 MQ"支付成功了"，就立即返回。其他服务（订单、短信、积分）自己去 MQ 订阅消息，异步处理。

text
用户支付 → 1.扣减余额（50ms）
         → 2.更新支付流水（50ms）
         → 3.发消息到 MQ（5ms）← 超级快
         → 立即返回"支付成功"（总耗时：105ms）

                   ↓ 异步处理（不影响返回）
         MQ → 订单服务（更新订单状态）
            → 短信服务（发通知）
            → 积分服务（给积分）

优势：

  • 耦合度低：支付不关心下游服务
  • 性能好：只管发消息，立即返回
  • 扩展性强：新增服务只需订阅消息
  • 故障隔离：短信服务挂了，不影响支付

劣势：

  • 依赖 MQ 可靠性
  • 架构复杂
  • 调试麻烦

1.4 什么时候用 MQ

✅ 适合用 MQ：

  • 下游服务不需要立即返回结果（发短信、发邮件、积分）
  • 需要解耦多个服务
  • 流量削峰（秒杀）

❌ 不适合用 MQ：

  • 需要立即得到结果（查询余额、登录验证）
  • 强事务场景

1.5 MQ 技术选型

RabbitMQ RocketMQ Kafka ActiveMQ
公司 Rabbit 阿里 Apache Apache
语言 Erlang Java Scala Java
吞吐量 一般 高 非常高 差
延迟 微秒级 毫秒级 毫秒级 毫秒级
可靠性 高 高 一般 一般
适合 业务消息 电商 大数据 老项目

💡 国内大多数业务项目用 RabbitMQ：可靠性高、延迟低、文档全、生态成熟。

第二章：RabbitMQ 核心概念

2.1 类比：快递站

把 RabbitMQ 类比成快递公司：

快递公司 RabbitMQ
快递员寄件 Publisher（生产者）发消息
快递分拨中心 Exchange（交换机）路由
快递仓库 Queue（队列）存消息
收件人取件 Consumer（消费者）收消息
快递公司 Virtual Host（虚拟主机）隔离

2.2 核心组件

text
Producer（生产者）
    ↓ 发消息
Exchange（交换机）——路由规则——→ Queue（队列）
                                    ↓ 推送
                              Consumer（消费者）
组件 作用
Publisher 发送消息的一方
Exchange 交换机，负责路由（本身不存消息！）
Queue 队列，存储消息，等消费者处理
Consumer 消费者，接收并处理消息
Virtual Host 虚拟主机，起到隔离作用（类似命名空间）
Binding 绑定，Exchange 和 Queue 的关系

⚠ 重要：交换机不存储消息！消息未路由到队列就会丢失！

2.3 安装 RabbitMQ（Docker 安装，推荐）

bash
docker run -d \
  -e RABBITMQ_DEFAULT_USER=itheima \     # 用户名
  -e RABBITMQ_DEFAULT_PASS=123321 \     # 密码
  -v mq-plugins:/plugins \              # 插件目录挂载
  --name mq \                            # 容器名
  --hostname mq \                        # 主机名
  -p 15672:15672 \                       # 管理控制台端口
  -p 5672:5672 \                         # 消息通信端口
  --network hmall \                      # 网络
  -d \                                   # 后台运行
  rabbitmq:3.8-management               # 镜像（带管理界面）

两个端口的作用：

  • 5672：应用程序发送/接收消息用
  • 15672：浏览器访问管理控制台用

访问管理界面：浏览器打开 http://服务器IP:15672，用 itheima/123321 登录。

2.4 管理控制台简介

登录后你会看到：

  • Overview：整体状态
  • Connections：连接数
  • Channels：信道
  • Exchanges：交换机列表
  • Queues：队列列表
  • Admin：用户管理

第三章：SpringAMQP 快速入门

3.1 什么是 AMQP

AMQP（Advanced Message Queuing Protocol）是消息队列的通信协议，就像 HTTP 是 Web 的协议一样。

SpringAMQP 是 Spring 对 AMQP 的封装，让我们用简单的 Java 代码操作 RabbitMQ。

3.2 准备工作

步骤 1：添加依赖

xml
<!-- pom.xml 中添加 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>

步骤 2：配置连接

yaml
# application.yaml
spring:
  rabbitmq:
    host: 192.168.150.101  # RabbitMQ 服务器地址
    port: 5672              # 端口（注意是 5672，不是 15672）
    virtual-host: /hmall   # 虚拟主机（需要提前在控制台创建）
    username: itheima       # 用户名
    password: 123321        # 密码

⚠ 新手常错：端口写成 15672（管理界面端口），应该是 5672（消息通信端口）。

3.3 发送消息（3 行代码）

java
@SpringBootTest
class PublisherTest {

    // 自动注入 RabbitTemplate（Spring 提供的发消息工具）
    @Autowired
    private RabbitTemplate rabbitTemplate;

    @Test
    void testSimpleQueue() {
        // 发送消息到指定队列
        // 参数 1：队列名称
        // 参数 2：消息内容（任意对象，自动序列化）
        rabbitTemplate.convertAndSend("hello.queue", "Hello, RabbitMQ!");
        System.out.println("消息发送成功");
    }
}

运行前先在控制台创建队列：Queues → Add a new queue → 输入名称 hello.queue → Add queue

3.4 接收消息（监听器）

java
@Component   // 让 Spring 管理这个类
public class MqListener {

    // @RabbitListener 注解：监听指定队列
    @RabbitListener(queues = "hello.queue")
    public void listenHelloQueue(String msg) {
        // msg 就是收到的消息内容，Spring 自动转换类型
        System.out.println("消费者收到消息：" + msg);
    }
}

3.5 完整流程

text
1. 生产者：rabbitTemplate.convertAndSend("hello.queue", "Hello!")
   ↓ 消息进入 hello.queue 队列
2. 消费者：@RabbitListener(queues = "hello.queue")
   ↓ 自动触发监听方法
3. 打印：消费者收到消息：Hello!

3.6 常见报错 ⚠

报错 1：AmqpConnectException: Connection refused

text
原因：连不上 RabbitMQ
解决：
1. 检查 RabbitMQ 是否启动（docker ps）
2. 检查 host、port、username、password 配置
3. 检查防火墙是否放行 5672 端口

报错 2：channel error; protocol method: #method<channel.close>

text
原因：队列不存在
解决：在控制台手动创建队列，或用注解自动声明（见后面）

报错 3：ACCESS_REFUSED - Login was refused

text
原因：用户名或密码错误
解决：检查 username 和 password 配置

第四章：WorkQueue（工作队列）

4.1 什么是 WorkQueue

类比：一个快递站（队列），有多个派送员（消费者）来取件。每个包裹（消息）只会被一个派送员取走，不会被多人重复取。

text
Queue（队列）
   ├── Consumer1 → 处理消息1、3、5...
   └── Consumer2 → 处理消息2、4、6...

作用：一个队列多个消费者，提高处理能力。

4.2 代码示例

发送 50 条消息：

java
@Test
void testWorkQueue() throws InterruptedException {
    for (int i = 1; i <= 50; i++) {
        // 发 50 条消息
        rabbitTemplate.convertAndSend("work.queue", "消息_" + i);
        Thread.sleep(20);    // 间隔 20ms，模拟发送频率
    }
}

两个消费者：

java
// 消费者 1（处理快，模拟 20ms 处理一条）
@RabbitListener(queues = "work.queue")
public void listenWorkQueue1(String msg) throws InterruptedException {
    System.out.println("消费者1 收到：" + msg + " ｜ " + LocalTime.now());
    Thread.sleep(20);   // 处理快
}

// 消费者 2（处理慢，模拟 200ms 处理一条）
@RabbitListener(queues = "work.queue")
public void listenWorkQueue2(String msg) throws InterruptedException {
    System.err.println("消费者2 收到：" + msg + " ｜ " + LocalTime.now());
    Thread.sleep(200);   // 处理慢
}

现象：默认情况下，两个消费者平均分配消息（各 25 条），即使消费者 1 处理很快也要等消费者 2 处理完。

4.3 能者多劳（prefetch）⭐

问题：消费者 1 处理快，空着等；消费者 2 处理慢，积压。浪费资源。

解决：设置 prefetch=1，每次只预取 1 条，处理完再取下一条。这样快的消费者自然拿到更多消息。

yaml
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1   # 每次只预取 1 条消息（能者多劳）

💡 prefetch 的原理：

  • 默认（prefetch=无限）：RabbitMQ 把消息平均分配，消费者一次性拿走一堆
  • prefetch=1：消费者只有处理完手头这条，才能再取一条

第五章：三种交换机（核心中的核心）⭐⭐⭐

5.1 交换机的作用

前面的 WorkQueue，消息直接发到队列。但实际项目中，往往需要"一条消息被多个服务处理"，这就需要交换机来路由。

text
没有交换机：
Producer → Queue → Consumer

有交换机：
Producer → Exchange → 路由 → Queue1 → Consumer1
                           → Queue2 → Consumer2
                           → Queue3 → Consumer3

三种交换机：

  • Fanout（广播）：消息发给所有绑定的队列
  • Direct（路由）：按 routingKey 精确匹配
  • Topic（主题）：按通配符匹配

5.2 Fanout 交换机（广播）⭐

类比：广播站，向所有听众广播同一条消息。

text
Exchange(Fanout)
    ├──→ queue1 → consumer1
    ├──→ queue2 → consumer2
    └──→ queue3 → consumer3

无论 routingKey 是什么，所有绑定的队列都会收到消息。

声明（注解方式，推荐）：

java
// 消费者 1（同时声明了交换机、队列、绑定关系）
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "fanout.queue1"),           // 队列名
    exchange = @Exchange(name = "hmall.fanout", type = ExchangeTypes.FANOUT)  // 交换机
))
public void listenFanoutQueue1(String msg) {
    System.out.println("消费者1 收到 fanout 消息：" + msg);
}

// 消费者 2
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "fanout.queue2"),
    exchange = @Exchange(name = "hmall.fanout", type = ExchangeTypes.FANOUT)
))
public void listenFanoutQueue2(String msg) {
    System.out.println("消费者2 收到 fanout 消息：" + msg);
}

发送消息：

java
// 发送到 Fanout 交换机
// 参数 1：交换机名称
// 参数 2：routingKey（Fanout 忽略这个参数，填 "" 即可）
// 参数 3：消息内容
rabbitTemplate.convertAndSend("hmall.fanout", "", "Hello, Fanout!");

运行结果：消费者 1 和消费者 2 都能收到这条消息。

使用场景：

  • 订单支付成功 → 通知订单服务、通知积分服务、通知短信服务（都要收）
  • 新用户注册 → 通知多个下游服务

5.3 Direct 交换机（路由）⭐⭐

类比：快递分拨中心，不同地区的快递路由到不同仓库。

text
Exchange(Direct)
    ├── red  ──→ queue1 → consumer1
    ├── blue ──→ queue2 → consumer2
    └── red  ──→ queue2 → consumer2（一个队列可以绑多个 key）

根据 routingKey 精确匹配，只有 key 匹配的队列才收到消息。

声明：

java
// 消费者 1：绑定 red 和 blue
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "direct.queue1"),
    exchange = @Exchange(name = "hmall.direct", type = ExchangeTypes.DIRECT),
    key = {"red", "blue"}    // 这个队列绑定了 red 和 blue 两个 key
))
public void listenDirectQueue1(String msg) {
    System.out.println("消费者1 收到 direct 消息：" + msg);
}

// 消费者 2：绑定 red 和 yellow
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "direct.queue2"),
    exchange = @Exchange(name = "hmall.direct", type = ExchangeTypes.DIRECT),
    key = {"red", "yellow"}
))
public void listenDirectQueue2(String msg) {
    System.out.println("消费者2 收到 direct 消息：" + msg);
}

发送消息：

java
// 发 red 消息 → queue1 和 queue2 都能收（都绑了 red）
rabbitTemplate.convertAndSend("hmall.direct", "red", "Red Message!");

// 发 blue 消息 → 只有 queue1 收（queue1 绑了 blue）
rabbitTemplate.convertAndSend("hmall.direct", "blue", "Blue Message!");

// 发 yellow 消息 → 只有 queue2 收
rabbitTemplate.convertAndSend("hmall.direct", "yellow", "Yellow Message!");

使用场景：

  • 不同级别的日志路由（ERROR 进 queue1，INFO 进 queue2）
  • 按区域路由（north 进北京仓，south 进广州仓）

5.4 Topic 交换机（主题）⭐⭐

类比：手机订阅号，china.* 订阅所有中国相关内容，*.news 订阅所有新闻。

通配符规则：

  • *：匹配一个单词
  • #：匹配零个或多个单词

示例：

text
china.#    匹配：china.news、china.weather、china.news.today
#.news     匹配：china.news、us.news、china.today.news
china.*    只匹配：china.news、china.weather（只有一个词）

声明：

java
// 消费者 1：订阅中国相关（china.#）
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "topic.queue1"),
    exchange = @Exchange(name = "hmall.topic", type = ExchangeTypes.TOPIC),
    key = "china.#"    // 通配符
))
public void listenTopicQueue1(String msg) {
    System.out.println("消费者1（china.#）收到：" + msg);
}

// 消费者 2：订阅所有新闻（#.news）
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "topic.queue2"),
    exchange = @Exchange(name = "hmall.topic", type = ExchangeTypes.TOPIC),
    key = "#.news"
))
public void listenTopicQueue2(String msg) {
    System.out.println("消费者2（#.news）收到：" + msg);
}

发送消息：

java
// china.news → 消费者 1 和消费者 2 都收（满足 china.# 和 #.news）
rabbitTemplate.convertAndSend("hmall.topic", "china.news", "中国新闻！");

// china.weather → 只有消费者 1 收（满足 china.#）
rabbitTemplate.convertAndSend("hmall.topic", "china.weather", "中国天气！");

// us.news → 只有消费者 2 收（满足 #.news）
rabbitTemplate.convertAndSend("hmall.topic", "us.news", "美国新闻！");

5.5 三种交换机对比 ⭐⭐⭐

交换机 路由规则 routingKey 适用场景
Fanout 广播，全部转发 忽略 需要所有服务都处理
Direct 精确匹配 key 完全相等 按类型分发
Topic 通配符匹配 *一词 #多词 按业务域分发

第六章：消息转换器

6.1 默认转换器的问题

默认用 Java 序列化（ObjectOutputStream），存到 RabbitMQ 里是乱码：

text
# 你发送的：Map{name: "jack", age: 18}
# RabbitMQ 里存的：
\xac\xed\x00\x05sr\x00\x11java.util.HashMap...（乱码）

缺点：

  • 可读性差（看不懂）
  • 体积大（序列化后很大）
  • 不安全（有反序列化漏洞）

6.2 配置 JSON 转换器

步骤 1：添加依赖

xml
<dependency>
    <groupId>com.fasterxml.jackson.dataformat</groupId>
    <artifactId>jackson-dataformat-xml</artifactId>
    <version>2.9.10</version>
</dependency>

步骤 2：在生产者和消费者都配置

java
@Bean
public MessageConverter messageConverter() {
    // 使用 JSON 序列化
    return new Jackson2JsonMessageConverter();
}

配置后效果：

java
// 发送 Map 对象
Map<String, Object> msg = new HashMap<>();
msg.put("name", "jack");
msg.put("age", 18);
rabbitTemplate.convertAndSend("object.queue", msg);

// RabbitMQ 里存的：{"name":"jack","age":18}（可读 JSON）

// 接收自动反序列化
@RabbitListener(queues = "object.queue")
public void listenObjectQueue(Map<String, Object> msg) {
    System.out.println(msg);    // {name=jack, age=18}
}

⚠ 注意：生产者和消费者都要配置 JSON 转换器，不然消费者无法正确反序列化。

第七章：声明队列和交换机的两种方式

7.1 方式一：Bean 配置类（代码声明）

java
@Configuration
public class FanoutConfig {

    // 声明 Fanout 交换机
    @Bean
    public FanoutExchange fanoutExchange() {
        return new FanoutExchange("hmall.fanout");
    }

    // 声明队列 1
    @Bean
    public Queue fanoutQueue1() {
        return new Queue("fanout.queue1");
    }

    // 声明队列 2
    @Bean
    public Queue fanoutQueue2() {
        return new Queue("fanout.queue2");
    }

    // 绑定队列 1 到交换机
    @Bean
    public Binding fanoutBinding1(Queue fanoutQueue1, FanoutExchange fanoutExchange) {
        return BindingBuilder.bind(fanoutQueue1).to(fanoutExchange);
    }

    // 绑定队列 2 到交换机
    @Bean
    public Binding fanoutBinding2(Queue fanoutQueue2, FanoutExchange fanoutExchange) {
        return BindingBuilder.bind(fanoutQueue2).to(fanoutExchange);
    }
}

7.2 方式二：注解声明（推荐）

java

// 支付服务：支付成功后发消息
@Service
public class PaymentService {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    @Transactional
    public void paySuccess(Long orderId) {
        // 1. 更新支付流水状态
        payMapper.updateStatus(orderId, PayStatus.SUCCESS);

        // 2. 发消息到 Topic 交换机（不用等下游）
        rabbitTemplate.convertAndSend(
            "pay.topic",          // 交换机
            "pay.success",        // routingKey
            orderId               // 消息内容（订单 ID）
        );

        log.info("支付成功消息已发送，orderId={}", orderId);
        // 立即返回，不等短信/积分/订单处理
    }
}

第九章：面试常问（附答案）

Q1：同步调用和异步调用的区别？

答：

  • 同步：调用后等待结果，是阻塞的
  • 异步：调用后立即返回，结果后续通过回调/消息获取

Q2：什么时候用 MQ？

答：

  • 下游不需要立即返回结果（短信、积分）
  • 需要解耦多个服务
  • 流量削峰（秒杀）

Q3：三种交换机类型及区别？

答：

Fanout Direct Topic
广播，忽略 key 精确匹配 key 通配符匹配（*一词，#多词）

Q4：Fanout 和 Direct 的区别？

答：Fanout 把消息发给所有绑定的队列，Direct 按 routingKey 精确路由。

Q5：交换机能存消息吗？

答：不能！ 交换机只负责路由，消息存在队列里。

Q6：什么是 prefetch？

答：消费者每次预取的消息数。默认无限制（平均分配），设为 1 实现能者多劳。

⚠ 新手易踩的坑

  1. 端口用 5672（通信），不是 15672（控制台）
  2. 交换机不存消息，不绑队列消息就丢了
  3. 生产者和消费者都要配置 JSON 转换器
  4. prefetch 默认无限，要设 1 才能实现能者多劳
  5. Topic 通配符：* 匹配 1 个词，# 匹配 0 或多个词
