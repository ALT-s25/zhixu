第一章：消息为什么会丢失

1.1 消息的旅途

一条消息从发送到消费，经过这些步骤：

text
生产者
  ↓ 1. 网络传输
Exchange（交换机）
  ↓ 2. 路由
Queue（队列）
  ↓ 3. 存储（内存/磁盘）
Consumer（消费者）
  ↓ 4. 处理

每一步都可能出问题：

丢失位置 原因 解决
生产者 → MQ 网络故障、Exchange 不存在 生产者重试 + 确认
MQ 内部 宕机、内存满、未持久化 持久化 + LazyQueue
MQ → 消费者 消费者宕机、处理异常 消费者确认 + 重试

第二章：发送者可靠性

2.1 生产者重试机制

场景：生产者和 MQ 之间网络不稳定，消息可能发不出去。

解决：配置重试，发送失败自动重试。

yaml
spring:
  rabbitmq:
    connection-timeout: 1s   # 连接超时时间
    template:
      retry:
        enabled: true             # 开启重试
        initial-interval: 1000ms  # 第 1 次重试等待 1 秒
        multiplier: 1             # 每次等待时长不变（1 × 1 = 1 秒）
        max-attempts: 3           # 最多重试 3 次

⚠ 注意：重试是阻塞式的，重试期间当前线程卡住了。对性能敏感的业务要谨慎开启。

2.2 生产者确认机制（Publisher Confirm）⭐⭐⭐

场景：消息发出去了，但不知道 MQ 有没有收到。

解决：RabbitMQ 提供回执（ACK/NACK），告诉生产者消息的状态。

text
生产者发消息
    ↓
MQ 收到后，发回执：
  - ACK：投递成功（到达交换机并入队）
  - NACK：投递失败（MQ 内部故障）
  - Return：路由失败（到达交换机，但没有匹配的队列）

状态流程图：

text
生产者 → 消息 → Exchange
                  │
         ┌────────┴─────────┐
         ↓                  ↓
      找到 Queue          没找到 Queue
         │                  │
     入队成功           Return 回执（路由失败）
         │
    ┌────┴────┐
    ↓         ↓
  临时消息   持久消息
  ACK       ACK（持久化完成后）

步骤 1：开启确认机制

yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated  # 开启 Confirm，异步回调
    publisher-returns: true             # 开启 Return

confirm-type 三种模式：

  • none：关闭（默认）
  • simple：同步等待 MQ 回执（阻塞，不推荐）
  • correlated：异步回调（推荐）

步骤 2：配置 ReturnCallback（路由失败时回调）

每个 RabbitTemplate 只能配置一个 ReturnCallback，放在配置类里：

java
@Slf4j
@AllArgsConstructor
@Configuration
public class MqConfig {

    private final RabbitTemplate rabbitTemplate;

    // Spring 启动后执行
    @PostConstruct
    public void init() {
        // 配置路由失败的回调
        rabbitTemplate.setReturnsCallback(returned -> {
            // returned 包含：消息内容、交换机、routingKey、失败原因
            log.error("消息路由失败！");
            log.error("  交换机：{}", returned.getExchange());
            log.error("  routingKey：{}", returned.getRoutingKey());
            log.error("  失败原因：{}", returned.getReplyText());
            log.error("  消息内容：{}", returned.getMessage());

            // 这里可以做：重新发送 / 存数据库 / 发告警
        });
    }
}

步骤 3：发送时添加 ConfirmCallback（投递结果回调）

每条消息的确认结果不同，所以 ConfirmCallback 要在发消息时设置：

java
@Test
void testPublisherConfirm() {
    // 1. 创建 CorrelationData（关联数据，包含消息 ID）
    CorrelationData correlationData = new CorrelationData(UUID.randomUUID().toString());

    // 2. 给 CorrelationData 添加回调
    correlationData.getFuture().addCallback(
        new ListenableFutureCallback<CorrelationData.Confirm>() {
            @Override
            public void onSuccess(CorrelationData.Confirm result) {
                // result.isAck()：true = ACK，false = NACK
                if (result.isAck()) {
                    log.info("消息投递成功，消息 ID：{}", correlationData.getId());
                } else {
                    // NACK：MQ 内部故障
                    log.error("消息投递失败！原因：{}", result.getReason());
                    // TODO：这里需要做补偿（重发 / 记录数据库）
                }
            }

            @Override
            public void onFailure(Throwable ex) {
                // 一般不会走这里
                log.error("消息发送异常：", ex);
            }
        }
    );

    // 3. 发送消息（带上 CorrelationData）
    rabbitTemplate.convertAndSend(
        "hmall.direct",       // 交换机
        "blue",               // routingKey
        "Hello, Confirm!",    // 消息内容
        correlationData        // 关联数据
    );
}

💡 注意：生产者确认消耗 MQ 性能，只在消息可靠性要求很高时开启。大多数情况下，开启 Return（路由失败告警）就够了，Confirm 可以不开。

第三章：MQ 可靠性（持久化）

3.1 数据持久化

默认情况下，MQ 的数据在内存中，重启就没了！

需要三处都持久化：

交换机持久化

java
// 注解声明时默认持久化
@Exchange(name = "hmall.direct", durable = "true")

// Bean 声明
new DirectExchange("hmall.direct", true, false);
// 参数：name, durable（持久化）, autoDelete（无队列时自动删除）

队列持久化

java
// 注解声明时默认持久化
@Queue(name = "direct.queue1", durable = "true")

// Bean 声明
QueueBuilder.durable("direct.queue1").build();

消息持久化

SpringAMQP 发送的消息默认已经是持久化的（DeliveryMode.PERSISTENT），不需要额外配置。

3.2 LazyQueue（惰性队列）⭐⭐

问题：默认队列数据存在内存中，消息堆积太多时：

  1. 内存占满
  2. RabbitMQ 把消息刷到磁盘（PageOut）
  3. PageOut 期间阻塞所有请求

LazyQueue 解决：消息直接存磁盘，内存只保留少量索引。

优点：

  • 支持百万级消息堆积
  • 不会因堆积而阻塞

缺点：

  • 读写稍慢（磁盘 IO）

配置方式 1：控制台

新建队列时，Arguments 添加 x-queue-mode = lazy

配置方式 2：Bean 声明

java
@Bean
public Queue lazyQueue() {
    return QueueBuilder
        .durable("lazy.queue")
        .lazy()   // 开启 Lazy 模式
        .build();
}

配置方式 3：注解声明

java
@RabbitListener(queuesToDeclare = @Queue(
    name = "lazy.queue",
    durable = "true",
    arguments = @Argument(name = "x-queue-mode", value = "lazy")
))
public void listenLazyQueue(String msg) {
    log.info("收到 lazy.queue 消息：{}", msg);
}

💡 RabbitMQ 3.12+ 版本：所有队列默认就是 Lazy 模式，不需要手动配置。

第四章：消费者可靠性 ⭐⭐⭐

4.1 消费者确认机制（ACK）

问题：MQ 把消息发给消费者，消费者收到了，但处理时崩溃了，消息丢失！

解决：消费者处理完后，向 MQ 发确认（ACK），MQ 才删除消息。

三种确认方式：

确认方式 含义 MQ 行为
ACK 处理成功 删除消息
NACK 处理失败 重新投递
REJECT 拒绝 重新投递或丢弃

配置确认模式：

yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto   # none / manual / auto

三种模式：

  • none：不确认，消息投递即删除（消息可能丢）
  • manual：手动确认（代码复杂，需要自己调 channel.basicAck()）
  • auto：自动确认（推荐）

auto 模式的行为：

  • 方法正常执行完 → 自动 ACK
  • 方法抛异常 → 自动 NACK（消息重新入队）

4.2 失败重试机制 ⭐⭐

问题：消费者处理失败，默认无限重投，CPU 飙升、消息堆积。

解决：配置本地重试，达到上限后换失败处理策略。

yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto
        retry:
          enabled: true             # 开启重试
          initial-interval: 1000ms  # 第 1 次重试等 1 秒
          multiplier: 1             # 等待倍数
          max-attempts: 3           # 最多重试 3 次
          stateless: true           # 无状态重试（有事务用 false）

执行流程：

text
消费者处理失败
    ↓ 等 1 秒
第 1 次重试（失败）
    ↓ 等 1 秒
第 2 次重试（失败）
    ↓ 等 1 秒
第 3 次重试（失败）
    ↓ 达到上限！
触发失败处理策略

4.3 失败处理策略 ⭐⭐

重试耗尽后，消息怎么处理？

策略 类 行为
丢弃（默认） RejectAndDontRequeueRecoverer 直接丢弃
重新入队 ImmediateRequeueMessageRecoverer 重新入队（可能死循环）
投到 error 队列 RepublishMessageRecoverer 推荐

配置投到 error 队列：

java
@Bean
public MessageRecoverer republishMessageRecoverer(RabbitTemplate rabbitTemplate) {
    // 失败的消息投递到 error.direct 交换机，routingKey=error
    return new RepublishMessageRecoverer(rabbitTemplate, "error.direct", "error");
}

// 同时声明 error 队列和交换机
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "error.queue", durable = "true"),
    exchange = @Exchange(name = "error.direct"),
    key = "error"
))
public void listenErrorQueue(Message message) {
    log.error("消息处理失败，进入 error 队列：{}", message);
    // 人工处理：查日志、修复 bug、手动重发
}

流程图：

text
消费者处理失败
    ↓ 重试 3 次
仍失败
    ↓
RepublishMessageRecoverer
    ↓
error.direct 交换机
    ↓
error.queue 队列
    ↓
人工处理（查原因、重发）

4.4 业务幂等性 ⭐⭐⭐（必须掌握）

什么是幂等性：同一操作执行多次，结果相同。

为什么需要：消息可能因网络原因被重复投递，消费者需要保证"同一消息处理多次等于只处理一次"。

方案一：唯一消息 ID

java
// 发送时设置唯一 ID
CorrelationData correlationData = new CorrelationData(UUID.randomUUID().toString());
rabbitTemplate.convertAndSend("exchange", "key", msg, correlationData);

// 消费时检查 ID（已处理过则跳过）
@RabbitListener(queues = "queue")
public void listen(String msg, Message message) {
    // 1. 获取消息 ID
    String msgId = message.getMessageProperties().getMessageId();

    // 2. 用 Redis 判断是否已处理
    //    setIfAbsent = set if not exists（SETNX）
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent("mq:msg:" + msgId, "1", 24, TimeUnit.HOURS);

    if (!BooleanUtil.isTrue(success)) {
        // 已处理过，直接跳过
        log.info("重复消息，跳过：{}", msgId);
        return;
    }

    // 3. 处理业务
    doProcess(msg);
}

方案二：业务判断（推荐）⭐

java
// 场景：支付成功后更新订单状态
@RabbitListener(queues = "pay.success.queue")
public void handlePaySuccess(Long orderId) {
    // 1. 查询订单当前状态
    Order order = orderService.getById(orderId);

    // 2. 判断：只有"未支付"状态的订单才处理
    if (order == null || order.getStatus() != OrderStatus.UNPAID) {
        // 已经处理过了（状态不是未支付）
        log.info("订单 {} 已处理，跳过", orderId);
        return;
    }

    // 3. 更新订单状态
    orderService.updateStatus(orderId, OrderStatus.PAID);
    log.info("订单 {} 状态更新为已支付", orderId);
}

💡 业务判断方案更推荐：

  • 不依赖消息 ID
  • 自然地利用业务状态机
  • 代码更清晰

第五章：延迟消息（订单超时取消）⭐⭐⭐

5.1 什么是延迟消息

延迟消息 = 消息发出后，等待一段时间再被消费。

应用场景：

  • 下单后 30 分钟未支付，自动取消订单
  • 外卖下单后 5 分钟推送"你的外卖已接单"
  • 定时提醒（明天 10 点会议）

5.2 方案一：TTL + 死信队列（了解）

死信（Dead Letter）：消息变成"死信"的三种情况：

  1. 消费者 NACK/REJECT（requeue=false）
  2. 消息 TTL 过期
  3. 队列消息数超过上限

思路：给消息设 TTL，过期后进入死信队列，消费者监听死信队列。

java
// 声明 TTL 队列（消息 10 秒后过期，进入死信交换机）
@Bean
public Queue ttlQueue() {
    return QueueBuilder.durable("ttl.queue")
        .ttl(10000)                            // 10 秒过期
        .deadLetterExchange("dl.direct")       // 死信交换机
        .deadLetterRoutingKey("dl")            // 死信 routingKey
        .build();
}

// 声明死信队列（接收过期消息）
@Bean
public Queue dlQueue() {
    return QueueBuilder.durable("dl.queue").build();
}

// 消费死信队列
@RabbitListener(queues = "dl.queue")
public void listenDlQueue(String msg) {
    log.info("收到延迟消息：{}", msg);
    // 此时消息已经"延迟"了 10 秒
}

⚠ 问题：TTL 是固定的，所有消息延迟一样。如果第一条消息延迟 30 分钟，后面的消息也要等这条处理完，后面的消息延迟更长。

5.3 方案二：DelayExchange 插件（推荐）⭐⭐

原理：交换机支持延迟投递，消息在交换机里等待，到时间才路由到队列。

步骤 1：安装插件

bash
# 把插件文件放到 RabbitMQ 插件目录
docker exec -it mq bash
rabbitmq-plugins enable rabbitmq_delayed_message_exchange
# 重启 RabbitMQ

步骤 2：声明延迟交换机

java
// 消费者：声明延迟交换机
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "delay.queue", durable = "true"),
    exchange = @Exchange(
        name = "delay.direct",
        delayed = "true",           // 开启延迟！
        type = ExchangeTypes.DIRECT
    ),
    key = "delay"
))
public void listenDelayQueue(String msg) {
    log.info("延迟消息到达：{}", LocalTime.now());
    log.info("消息内容：{}", msg);
}

步骤 3：发送延迟消息

java
@Test
void testDelayMessage() throws InterruptedException {
    log.info("发送消息：{}", LocalTime.now());

    // 通过 MessagePostProcessor 设置延迟时间（毫秒）
    rabbitTemplate.convertAndSend(
        "delay.direct",
        "delay",
        "Hello, Delay!",
        message -> {
            // 设置延迟 5 秒（5000 毫秒）
            message.getMessageProperties().setDelay(5000);
            return message;
        }
    );

    Thread.sleep(10000);  // 等 10 秒，让消息到达
}

运行结果：

text
发送消息：10:30:00.123
延迟消息到达：10:30:05.456  ← 5 秒后到达
消息内容：Hello, Delay!

⚠ 生产注意：DelayExchange 消息存在交换机内存中，RabbitMQ 重启会丢失！需要配合消息持久化使用。

第六章：实战案例——订单超时取消 ⭐⭐⭐

6.1 业务流程

text
用户下单
    ↓
发送延迟消息（30 分钟后检查支付状态）
    ↓ 30 分钟
消费者收到消息
    ↓
查询订单状态
    ├── 已支付 → 忽略
    └── 未支付 → 取消订单 + 恢复库存

6.2 完整代码

定义常量：

java
public interface MqConstants {
    // 延迟交换机
    String DELAY_EXCHANGE = "trade.delay.topic";
    // 延迟队列
    String DELAY_ORDER_QUEUE = "trade.order.delay.queue";
    // routingKey
    String DELAY_ORDER_ROUTING_KEY = "order.query";
    // 超时时间（毫秒）：30 分钟 = 1800000
    int ORDER_TIMEOUT_MILLIS = 1800000;
}

下单时发延迟消息：

java
@Service
public class OrderService {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    @Transactional
    public Long createOrder(OrderFormDTO orderDTO) {
        // 1. 保存订单（省略）
        Long orderId = saveOrder(orderDTO);

        // 2. 发延迟消息（30 分钟后检查支付状态）
        rabbitTemplate.convertAndSend(
            MqConstants.DELAY_EXCHANGE,           // 延迟交换机
            MqConstants.DELAY_ORDER_ROUTING_KEY,  // routingKey
            orderId,                               // 消息内容（订单 ID）
            msg -> {
                // 设置延迟时间
                msg.getMessageProperties().setDelay(MqConstants.ORDER_TIMEOUT_MILLIS);
                return msg;
            }
        );

        log.info("订单 {} 创建成功，30 分钟后检查支付状态", orderId);
        return orderId;
    }
}

消费者：检查支付，超时则取消：

java
@Component
@Slf4j
public class OrderTimeoutListener {

    @Autowired
    private OrderService orderService;

    @Autowired
    private PaymentService paymentService;

    @RabbitListener(bindings = @QueueBinding(
        value = @Queue(name = MqConstants.DELAY_ORDER_QUEUE, durable = "true"),
        exchange = @Exchange(
            name = MqConstants.DELAY_EXCHANGE,
            delayed = "true",
            type = ExchangeTypes.TOPIC
        ),
        key = MqConstants.DELAY_ORDER_ROUTING_KEY
    ))
    public void checkOrderPayStatus(Long orderId) {
        log.info("检查订单支付状态，orderId={}", orderId);

        // 1. 查询订单
        Order order = orderService.getById(orderId);
        if (order == null) {
            // 订单不存在（可能已被删除）
            return;
        }

        // 2. 已支付，忽略
        if (order.getStatus() == OrderStatus.PAID) {
            log.info("订单 {} 已支付，不处理", orderId);
            return;
        }

        // 3. 未支付，调用支付服务查支付状态
        boolean isPaid = paymentService.checkPayStatus(orderId);
        if (isPaid) {
            // 支付了但订单状态没更新（补偿）
            orderService.updateStatus(orderId, OrderStatus.PAID);
            return;
        }

        // 4. 确实未支付，取消订单
        log.info("订单 {} 超时未支付，自动取消", orderId);
        orderService.cancelOrder(orderId);
    }
}

消费者
├── ACK 自动确认（异常时 NACK 重投）
├── 本地重试（最多 3 次）
├── RepublishMessageRecoverer（失败进 error 队列人工处理）
└── 业务幂等性（防重复消费）

7.2 什么情况下需要什么配置

场景 需要配置
一般业务（短信、积分） ACK auto + 本地重试 + error 队列
重要业务（支付、订单） 生产者确认 + 持久化 + ACK auto + 幂等
大流量业务（秒杀） LazyQueue + 异步处理
定时任务（超时取消） DelayExchange 插件

第八章：常见报错与解决

报错 1：消息重复消费

text
现象：同一条消息被消费了多次
原因：消费者处理成功但 ACK 失败，MQ 重新投递
解决：业务幂等性（方案二：业务判断）

报错 2：消息堆积，MQ 内存告警

text
现象：RabbitMQ 管理界面显示内存使用率过高
原因：消费者处理速度慢，消息积压
解决：
1. 配置 LazyQueue（消息存磁盘）
2. 增加消费者数量
3. 增大 prefetch 数量

报错 3：延迟消息没有延迟

text
现象：发送延迟消息后，立即被消费（没有等待）
原因 1：没有安装 rabbitmq_delayed_message_exchange 插件
原因 2：交换机没有设置 delayed = true
解决：确认插件安装，确认注解配置

报错 4：生产者确认回调没触发

text
现象：消息发出去了，但 ConfirmCallback 没有回调
原因：没有开启 publisher-confirm-type: correlated
解决：检查 application.yaml 配置

报错 5：error 队列 Bean 没有注册

text
现象：RepublishMessageRecoverer Bean 注入失败
原因：RabbitTemplate 还没初始化就注入了
解决：用构造器注入，或加 @Lazy 注解

第九章：面试常问（附答案）

Q1：如何保证消息不丢失？

答（三个环节）：

  • 生产者：Confirm + Return 确认，NACK 时重发
  • MQ：交换机/队列/消息持久化，LazyQueue
  • 消费者：ACK 确认，失败重试，error 队列人工处理

Q2：如何保证消息不重复消费？

答：业务幂等性：

  1. 业务判断（查状态，已处理则跳过）—— 推荐
  2. 唯一消息 ID + Redis 去重

Q3：死信队列是什么？

答：消息变成死信的三种情况：

  1. 消费者 NACK（requeue=false）
  2. 消息 TTL 过期
  3. 队列满了

死信会被路由到死信交换机，可以用来实现延迟消息（TTL + 死信）。

Q4：延迟消息的两种实现方案？

答：

  1. TTL + 死信队列：TTL 固定，前面消息阻塞后面的
  2. DelayExchange 插件：每条消息可设不同延迟时间（推荐）

Q5：消息堆积怎么解决？

答：

  1. 配置 LazyQueue（消息存磁盘，不占内存）
  2. 增加消费者数量（提高消费速度）
  3. 增大 prefetch（消费者批量处理）

Q6：生产者确认的两种回执？

答：

  • Confirm（ACK/NACK）：消息到达交换机的结果
  • Return：消息路由失败（到交换机了，但没找到队列）

第十章：本章小结

✅ 你已经掌握

  • 消息丢失的三个环节
  • 生产者重试 + 确认（Confirm/Return）
  • 数据持久化（交换机/队列/消息）
  • LazyQueue（防堆积崩溃）
  • 消费者 ACK 自动确认
  • 失败重试 + RepublishMessageRecoverer
  • 业务幂等性（优先业务判断）
  • 延迟消息：TTL 死信 vs DelayExchange 插件
  • 订单超时取消完整实现

⚠ 新手易踩的坑

  1. 生产者确认消耗 MQ 性能，非必要不开
  2. LazyQueue 在 3.12+ 已是默认，低版本要手动设置
  3. 延迟消息要安装 rabbitmq_delayed_message_exchange 插件
  4. error 队列要有人监控（人工处理）
  5. 重试次数不要太多（3 次够了），次数多了延迟大

💡 学习建议： RabbitMQ 高级的核心是"消息可靠性"三个字。记住：生产者确认、持久化、消费者 ACK、幂等性，这四点对应消息从发出到消费的每个环节。 延迟消息（订单超时）是实际项目高频需求，建议把完整代码跑通。
