第一章：短信登录（热身）

1.1 先讲问题：Session 不共享

故事：你做了个网站，用户登录后信息存在 Session 里。一台服务器扛不住，加了第二台。但用户登录时打到服务器 A，第二次请求打到服务器 B，B 没有这个用户的 Session，用户就被踢出去了。

text
用户登录 → 服务器 A（存 Session）
用户请求 → 服务器 B（没有 Session！）❌ 被踢出

解决：用 Redis 代替 Session，所有服务器共享。

1.2 Redis 代替 Session 的设计

text
发送验证码：
  手机号 → 生成 4~6 位验证码 → 存 Redis
  key = "login:code:13800138000"
  value = "123456"
  TTL = 2 分钟

登录验证：
  手机号 + 验证码 → 校验 Redis 里的验证码
  → 查询/创建用户 → 生成 token（UUID）
  → 存 Redis
  key = "login:token:abc123"
  value = 用户信息（JSON）
  TTL = 30 分钟
  → 返回 token 给前端

每次请求：
  前端带 token → 拦截器查 Redis → 刷新 TTL → 放行

1.3 完整代码（每行注释）

java
// ================== 发送验证码 ==================
@PostMapping("/code")
public Result sendCode(@RequestParam String phone) {
    // 1. 生成验证码（6 位数字）
    String code = RandomUtil.randomNumbers(6);

    // 2. 存入 Redis（key = login:code:手机号，2 分钟过期）
    stringRedisTemplate.opsForValue().set(
        "login:code:" + phone,   // key
        code,                      // value
        2, TimeUnit.MINUTES        // 过期时间
    );

    // 3. 发送短信（这里模拟）
    log.info("发送验证码成功：{}", code);
    return Result.ok();
}

// ================== 登录 ==================
@PostMapping("/login")
public Result login(@RequestBody LoginFormDTO form) {
    String phone = form.getPhone();
    String code = form.getCode();

    // 1. 从 Redis 取验证码
    String redisCode = stringRedisTemplate.opsForValue().get("login:code:" + phone);

    // 2. 校验验证码
    if (redisCode == null || !redisCode.equals(code)) {
        return Result.fail("验证码错误");
    }

    // 3. 查询用户（不存在则创建）
    User user = userService.queryByPhone(phone);
    if (user == null) {
        user = createUserWithPhone(phone);   // 新用户自动注册
    }

    // 4. 生成 token（UUID，不包含敏感信息）
    String token = UUID.randomUUID().toString();

    // 5. 把用户信息存入 Redis（用 Hash 存）
    //    key = login:token:token
    //    TTL = 30 分钟
    UserDTO userDTO = new UserDTO();
    userDTO.setId(user.getId());
    userDTO.setNickName(user.getNickName());
    userDTO.setIcon(user.getIcon());

    stringRedisTemplate.opsForHash().putAll(
        "login:token:" + token,
        BeanUtil.beanToMap(userDTO)
    );
    stringRedisTemplate.expire("login:token:" + token, 30, TimeUnit.MINUTES);

    // 6. 返回 token 给前端
    return Result.ok(token);
}

1.4 登录拦截器（每次请求都拦截）

java
public class LoginInterceptor implements HandlerInterceptor {

    private StringRedisTemplate stringRedisTemplate;

    // 构造器注入（拦截器不被 Spring 管理，要手动传）
    public LoginInterceptor(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean preHandle(HttpServletRequest request,
                              HttpServletResponse response,
                              Object handler) {
        // 1. 从请求头获取 token
        String token = request.getHeader("authorization");
        if (StrUtil.isBlank(token)) {
            response.setStatus(401);   // 401 = 未授权
            return false;
        }

        // 2. 从 Redis 查用户信息
        String key = "login:token:" + token;
        Map<Object, Object> userMap = stringRedisTemplate.opsForHash().entries(key);

        // 3. 用户不存在（token 无效或过期）
        if (userMap.isEmpty()) {
            response.setStatus(401);
            return false;
        }

        // 4. 刷新 token 的 TTL（每次请求都续期，活跃用户不掉线）
        stringRedisTemplate.expire(key, 30, TimeUnit.MINUTES);

        // 5. 用户信息存入 ThreadLocal（后续业务可以拿到）
        UserDTO userDTO = BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false);
        UserHolder.saveUser(userDTO);

        return true;   // 放行
    }

    @Override
    public void afterCompletion(HttpServletRequest request,
                                  HttpServletResponse response,
                                  Object handler, Exception ex) {
        // 请求结束，清理 ThreadLocal（防止内存泄漏）
        UserHolder.removeUser();
    }
}

第二章：商户查询缓存（核心中的核心）

2.1 什么是缓存

缓存就是把经常要查的数据，从数据库复制一份到 Redis，下次直接从 Redis 取，不用每次都查数据库。

text
第一次请求：
  客户端 → 服务端 → 查 MySQL → 返回数据
                          ↓
                     同时存一份到 Redis

第二次请求：
  客户端 → 服务端 → 查 Redis（命中）→ 返回数据
                  （不查 MySQL 了！）

2.2 基础缓存代码

java
public Shop queryShopById(Long id) {
    // 1. 拼 key（规范：业务:类型:ID）
    String key = "cache:shop:" + id;

    // 2. 从 Redis 查
    String json = stringRedisTemplate.opsForValue().get(key);

    // 3. 命中缓存（json 不是空，也不是空字符串）
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, Shop.class);   // JSON 转 Shop 对象
    }

    // 4. 命中空值（防穿透，后面讲）
    if (json != null) {
        // json 是 ""，说明是之前缓存了空值
        return null;
    }

    // 5. 查数据库
    Shop shop = shopMapper.selectById(id);
    if (shop == null) {
        // 数据库也没有，缓存空值防穿透（2 分钟过期）
        stringRedisTemplate.opsForValue().set(key, "", 2, TimeUnit.MINUTES);
        return null;
    }

    // 6. 写入缓存（30 分钟过期）
    stringRedisTemplate.opsForValue().set(
        key,
        JSONUtil.toJsonStr(shop),
        30, TimeUnit.MINUTES
    );

    return shop;
}

💡 StrUtil.isNotBlank 是 Hutool 工具，表示"不是 null 且不是空字符串"。 isNotBlank = false 的情况：null、""、纯空格。这里区分两种"空"很重要。

第三章：缓存更新策略（面试必问）

3.1 三种策略对比

策略 说明 一致性 维护成本
内存淘汰 Redis 自己满了自动删 差 低
超时剔除 给 key 设 TTL，到期自动删 一般 低
主动更新 修改 DB 后，手动删缓存 好 高

生产推荐：主动更新 + 超时剔除（兜底）

3.2 主动更新的三种方案

方案 说明 优缺点
Cache Aside 自己维护（代码写） 推荐，最常用
Write Through 缓存代理写 DB 强一致，但复杂
Write Behind 先写缓存，异步写 DB 性能好，但可能丢数据

3.3 Cache Aside 的写操作顺序（重要！）⭐⭐⭐

问题：修改数据库时，缓存怎么办？

有两种顺序：

  1. 先删缓存，再改 DB
  2. 先改 DB，再删缓存

为什么推荐"先改 DB，再删缓存"？

看"先删缓存，再改 DB"会发生什么：

text
时刻 1：线程 A 要改数据，先删了缓存
时刻 2：线程 B 来查，缓存没有，查 DB（旧值）
时刻 3：线程 B 把旧值写入缓存
时刻 4：线程 A 改了 DB（新值）
结果：缓存是旧值，DB 是新值，不一致！

看"先改 DB，再删缓存"：

text
时刻 1：线程 A 改 DB（新值）
时刻 2：线程 B 来查，命中缓存（旧值）→ 返回
时刻 3：线程 A 删缓存
时刻 4：线程 C 来查，缓存没了，查 DB（新值）→ 写入缓存
结果：只有时刻 2 那一瞬间是旧值，概率极低

⚠ 结论：Cache Aside 用"先改 DB，再删缓存"。注意是删缓存，不是改缓存（让下次查询时重新加载）。

第四章：缓存三大问题（重中之重）⭐⭐⭐⭐⭐

4.1 缓存穿透

问题：用户请求一个不存在的 key，Redis 没有，每次都打到数据库。如果有人恶意攻击，疯狂请求不存在的 ID，数据库就被打挂了。

text
攻击者 → 请求 id=-1 → Redis 没有 → 查 MySQL → MySQL 也没有
攻击者 → 请求 id=-2 → Redis 没有 → 查 MySQL → MySQL 也没有
... 无限循环，MySQL 挂了

解决方案：

方案 原理 优缺点
缓存空值 不存在也缓存 null，短过期 简单，但占内存
布隆过滤器 预先加载存在的 key，请求先过布隆 省内存，但有误判率

方案一：缓存空值（推荐，简单）

java
public Shop queryShopById(Long id) {
    String key = "cache:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);

    // 命中（有数据）
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, Shop.class);
    }

    // 命中空值（防穿透！json 是 ""，不是 null）
    if (json != null) {
        return null;
    }

    // 查数据库
    Shop shop = shopMapper.selectById(id);
    if (shop == null) {
        // 数据库也没有 → 缓存空值，2 分钟过期
        // 为什么短过期？万一以后新增了这个数据呢
        stringRedisTemplate.opsForValue().set(key, "", 2, TimeUnit.MINUTES);
        return null;
    }

    // 写入缓存
    stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), 30, TimeUnit.MINUTES);
    return shop;
}

💡 为什么用空字符串 "" 而不是 null？ Redis 里存的就是字符串，没法存 null。用 "" 表示"查过了，确实没有"。 isNotBlank("") = false（不是有数据），"" != null = true（是空值），巧妙区分。

4.2 缓存雪崩

问题：大量 key 同时过期，或者 Redis 宕机，所有请求打到数据库。

text
0 点 → 批量缓存了 1 万个商品，TTL 都是 30 分钟
30:00 → 1 万个 key 同时过期
30:01 → 1 万个请求同时查 MySQL → MySQL 挂了

解决方案：

  1. 给 TTL 加随机值（避免同时过期）⭐ 推荐

    java
    // 30 分钟 + 随机 0~5 分钟
int ttl = 30 + RandomUtil.randomInt(0, 5);
redisTemplate.opsForValue().set(key, json, ttl, TimeUnit.MINUTES);

  2. Redis 集群（主从 + 哨兵，Redis 挂了有备用）

  3. 降级限流（数据库扛不住时，限制请求量）

  4. 多级缓存（本地缓存 + Redis）

4.3 缓存击穿

问题：热点 key 过期的瞬间，大量请求同时打到数据库。

text
双 11 → 商品 id=1 是爆款，缓存 30 分钟
30:00 → 缓存过期
30:00.001 → 1 万人同时查 id=1 → Redis 没有 → 1 万人同时查 MySQL → MySQL 挂了

两种解决方案：

方案 原理 一致性 可用性
互斥锁 只让一个线程查 DB，其他等待 强一致 低（等待）
逻辑过期 key 不过期，后台异步更新 弱一致 高

方案一：互斥锁 ⭐⭐

思路：缓存失效时，只有一个线程能查数据库重建缓存，其他线程等待重试。

java
public Shop queryShopById(Long id) {
    String key = "cache:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);

    // 1. 命中缓存
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, Shop.class);
    }

    // 2. 命中空值
    if (json != null) {
        return null;
    }

    // 3. 缓存未命中，尝试获取互斥锁
    String lockKey = "lock:shop:" + id;
    Shop shop = null;
    try {
        boolean isLock = tryLock(lockKey);
        if (!isLock) {
            // 没拿到锁，等一会儿重试
            Thread.sleep(50);
            return queryShopById(id);   // 递归重试
        }

        // 4. DoubleCheck：拿到锁后再查一次缓存（可能别人刚重建好）
        json = stringRedisTemplate.opsForValue().get(key);
        if (StrUtil.isNotBlank(json)) {
            return JSONUtil.toBean(json, Shop.class);
        }

        // 5. 查数据库
        shop = shopMapper.selectById(id);
        if (shop == null) {
            stringRedisTemplate.opsForValue().set(key, "", 2, TimeUnit.MINUTES);
            return null;
        }

        // 6. 写入缓存
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), 30, TimeUnit.MINUTES);
    } catch (InterruptedException e) {
        throw new RuntimeException(e);
    } finally {
        // 7. 释放锁
        unlock(lockKey);
    }
    return shop;
}

// 获取锁（SETNX + 过期时间，原子操作）
private boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue()
        .setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
    return BooleanUtil.isTrue(flag);
}

// 释放锁
private void unlock(String key) {
    stringRedisTemplate.delete(key);
}

💡 互斥锁的缺点：线程等待，性能有损失。但保证强一致性。

方案二：逻辑过期 ⭐⭐

思路：key 永不过期（不设 TTL），但 value 里带一个"逻辑过期时间"。过期后，第一个请求触发异步重建，其他请求返回旧数据。

java
// 包装类：包含数据和逻辑过期时间
@Data
public class RedisData {
    private LocalDateTime expireTime;   // 逻辑过期时间
    private Object data;                // 实际数据
}

// 线程池：异步重建缓存
private static final ExecutorService CACHE_REBUILD_EXECUTOR =
    Executors.newFixedThreadPool(10);

public Shop queryWithLogicalExpire(Long id) {
    String key = "cache:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);

    // 1. 缓存不存在（理论上不会，热点数据提前预热）
    if (StrUtil.isBlank(json)) {
        return null;
    }

    // 2. 反序列化
    RedisData redisData = JSONUtil.toBean(json, RedisData.class);
    Shop shop = JSONUtil.toBean((JSONObject) redisData.getData(), Shop.class);
    LocalDateTime expireTime = redisData.getExpireTime();

    // 3. 未过期 → 直接返回
    if (expireTime.isAfter(LocalDateTime.now())) {
        return shop;
    }

    // 4. 已过期 → 尝试获取锁，异步重建
    String lockKey = "lock:shop:" + id;
    if (tryLock(lockKey)) {
        // 拿到锁，异步重建缓存
        CACHE_REBUILD_EXECUTOR.submit(() -> {
            try {
                // DoubleCheck
                RedisData rd = JSONUtil.toBean(
                    stringRedisTemplate.opsForValue().get(key), RedisData.class);
                if (rd.getExpireTime().isAfter(LocalDateTime.now())) {
                    return;   // 别人已经重建了
                }

                // 查数据库，写入缓存
                Shop newShop = shopMapper.selectById(id);
                saveShop2Redis(id, 30L);   // 逻辑过期 30 分钟
            } finally {
                unlock(lockKey);
            }
        });
    }

    // 5. 返回旧数据（不等待重建完成）
    return shop;
}

// 把数据写入 Redis（带逻辑过期时间）
public void saveShop2Redis(Long id, Long expireSeconds) {
    Shop shop = shopMapper.selectById(id);
    RedisData redisData = new RedisData();
    redisData.setData(shop);
    redisData.setExpireTime(LocalDateTime.now().plusSeconds(expireSeconds));
    stringRedisTemplate.opsForValue().set("cache:shop:" + id, JSONUtil.toJsonStr(redisData));
}

💡 逻辑过期的优势：所有请求都能立即返回（要么新数据要么旧数据），不会阻塞。缺点是短暂返回旧数据。

两种方案对比 ⭐

互斥锁 逻辑过期
一致性 强（等待最新数据） 弱（短暂旧数据）
可用性 低（等待锁） 高（立即返回）
实现复杂度 中 高（需要预热）
适合 数据要求精确 高并发、可容忍短暂不一致

4.4 三大问题总结 ⭐⭐⭐

问题 现象 解决方案
穿透 查不存在的数据 缓存空值 / 布隆过滤器
雪崩 大量 key 同时过期 随机 TTL / 集群 / 限流
击穿 热点 key 过期 互斥锁 / 逻辑过期

💡 记忆口诀：

  • 穿透 = 查不到 → 缓存空值
  • 雪崩 = 大量倒 → 加随机 TTL
  • 击穿 = 热点倒 → 加锁重建

第五章：秒杀设计（项目核心）

5.1 全局唯一 ID

为什么需要：秒杀订单 ID 不能用数据库自增（分库分表会冲突，且暴露销量）。

要求：唯一、递增、高性能、安全。

设计方案：时间戳 + 序列号

text
ID = 时间戳(31位) | 序列号(32位)
    ↑                ↑
    秒数(从2022年起)  Redis 自增（每天重置）
java
@Component
public class RedisIdWorker {

    // 起始时间戳（2022-01-01 00:00:00）
    private static final long BEGIN_TIMESTAMP = 1640995200L;

    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    public long nextId(String keyPrefix) {
        // 1. 生成时间戳
        LocalDateTime now = LocalDateTime.now();
        long nowSecond = now.toEpochSecond(ZoneOffset.UTC);
        long timestamp = nowSecond - BEGIN_TIMESTAMP;

        // 2. 生成序列号（Redis 自增）
        // key 包含日期，每天自增从 0 开始
        String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
        long count = stringRedisTemplate.opsForValue()
            .increment("icr:" + keyPrefix + ":" + date);

        // 3. 拼接（时间戳左移 32 位 + 序列号）
        return timestamp << 32 | count;
    }
}

💡 为什么要加日期？key 包含日期，每天的 count 从 0 开始，不会无限增长。

5.2 超卖问题 ⭐⭐⭐

问题：库存只剩 1 个，两个用户同时下单，都看到"有库存"，都下单成功 → 超卖。

解决：乐观锁

不用真的加锁，而是在更新时加条件判断：

java
// ❌ 错误做法：先查再改（有并发问题）
Integer stock = voucherMapper.getStock(voucherId);
if (stock > 0) {
    voucherMapper.updateStock(voucherId, stock - 1);   // 可能已被别人改了
}

// ✅ 乐观锁：一条 SQL 搞定
// UPDATE voucher SET stock = stock - 1
// WHERE id = ? AND stock > 0
boolean success = seckillVoucherService.update()
    .setSql("stock = stock - 1")            // set stock = stock - 1
    .eq("voucher_id", voucherId)             // where voucher_id = ?
    .gt("stock", 0)                          // and stock > 0
    .update();

if (!success) {
    return Result.fail("库存不足");
}

💡 为什么叫"乐观锁"？因为乐观地认为"大多数情况下不会冲突"，不加锁，只在最后更新时判断条件。

5.3 一人一单 ⭐⭐

问题：用户疯狂点击，一个用户下了多单。

单机解决：用 synchronized 锁住用户 ID

java
// ❌ 单机版（集群下无效）
synchronized (userId.toString().intern()) {
    // 查订单、下单
}

集群问题：synchronized 只锁当前 JVM，多台服务器之间无效。

解决：分布式锁（下一章详解）

第六章：分布式锁 ⭐⭐⭐⭐⭐（最重要）

6.1 为什么需要分布式锁

故事：你有 3 台服务器，用户 A 在服务器 1 上下了单，服务器 1 用 synchronized 锁住了。但用户 A 又在服务器 2 上点了下单，服务器 2 不知道服务器 1 锁了，又让他下单成功 → 重复下单。

text
服务器1：synchronized(用户A) → 下单成功
服务器2：synchronized(用户A) → 也下单成功 ❌（不知道服务器1锁了）

分布式锁：所有服务器都去 Redis 上锁，谁先抢到谁能下单。

6.2 自实现分布式锁（SETNX）

核心思路：用 SETNX（不存在才设置），谁设置成功谁拿到锁。

java
public boolean tryLock(String lockKey, String requestId, long expireTime) {
    // SETNX + 过期时间（原子操作）
    Boolean flag = stringRedisTemplate.opsForValue()
        .setIfAbsent(lockKey, requestId, expireTime, TimeUnit.SECONDS);
    return BooleanUtil.isTrue(flag);
}

public void unlock(String lockKey, String requestId) {
    // 先判断是不是自己的锁，再删除
    // 但这两步不是原子的，有坑！后面用 Lua 解决
    String value = stringRedisTemplate.opsForValue().get(lockKey);
    if (requestId.equals(value)) {
        stringRedisTemplate.delete(lockKey);
    }
}

6.3 三个核心问题与解决

问题 1：锁误删

场景：线程 A 拿到锁，业务卡了 10 秒。锁 5 秒后自动过期，线程 B 拿到锁。线程 A 终于执行完，把锁删了（删的是 B 的锁！）

解决：锁里存"谁加的锁"（线程 ID），删之前判断是不是自己的。

java
// 加锁时存线程 ID
String threadId = Thread.currentThread().getId() + "";
redisTemplate.opsForValue().setIfAbsent(lockKey, threadId, 10, TimeUnit.SECONDS);

// 释放锁时先判断
String value = redisTemplate.opsForValue().get(lockKey);
if (threadId.equals(value)) {
    redisTemplate.delete(lockKey);
}

问题 2：判断 + 删除不原子

场景：判断完是自己的锁，正要删，锁过期了，B 拿到锁，A 把 B 的锁删了。

解决：用 Lua 脚本保证原子性

java
// Lua 脚本：判断 + 删除一步完成
String script =
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +   // 判断是不是自己的
    "  return redis.call('del', KEYS[1]) " +              // 是就删
    "else " +
    "  return 0 " +                                        // 不是就不删
    "end";

Long result = stringRedisTemplate.execute(
    new DefaultRedisScript<>(script, Long.class),
    Collections.singletonList(lockKey),    // KEYS[1]
    threadId                                 // ARGV[1]
);

问题 3：不可重入

场景：同一个线程想多次获取同一把锁（递归调用），第二次获取失败。

解决：用 Hash 存锁次数（Redisson 实现）

6.4 Redisson（推荐，生产用这个）⭐⭐⭐

自实现的锁问题太多，生产环境用 Redisson 框架。

依赖：

xml
<dependency>
    <groupId>org.redisson</groupId>
    <artifactId>redisson-spring-boot-starter</artifactId>
    <version>3.13.6</version>
</dependency>

配置：

java
@Bean
public RedissonClient redissonClient() {
    Config config = new Config();
    config.useSingleServer()
        .setAddress("redis://192.168.150.101:6379")
        .setPassword("123321");
    return Redisson.create(config);
}

使用：

java
@Autowired
private RedissonClient redissonClient;

public Result createOrder(Long userId) {
    // 1. 获取锁（参数：锁名）
    RLock lock = redissonClient.getLock("lock:order:" + userId);

    // 2. 尝试加锁
    // tryLock(等待时间, 锁超时时间, 时间单位)
    boolean isLock = lock.tryLock(1, 10, TimeUnit.SECONDS);

    if (!isLock) {
        return Result.fail("请勿重复下单");
    }

    try {
        // 3. 业务逻辑（查订单、下单）
        return createOrderInternal(userId);
    } finally {
        // 4. 释放锁
        lock.unlock();
    }
}

6.5 Redisson 的核心机制 ⭐⭐

可重入锁

同一个线程可以多次获取同一把锁，内部用 Hash 存次数：

text
key = lock:order:1
value = {
    "线程ID": 2    // 获取了 2 次
}

WatchDog（看门狗）⭐⭐

问题：锁超时时间设短了，业务没执行完锁就过期了；设长了，进程崩了锁要等很久。

WatchDog 解决：不设超时时间时，WatchDog 默认 30 秒，每 10 秒自动续期。进程崩了就不再续期，锁自动过期。

text
获取锁（不设超时）→ WatchDog 启动
  ↓ 每 10 秒
  续期到 30 秒
  ↓ ...
业务完成 → 释放锁 → WatchDog 停止

⚠ 注意：WatchDog 只在不传超时时间时生效。如果传了 lock.tryLock(1, 10, SECONDS)，就不会有 WatchDog。

联锁（MultiLock）

多 Redis 实例上加锁，防单点故障：

java
RLock lock1 = redissonClient1.getLock("lock1");
RLock lock2 = redissonClient2.getLock("lock2");
RLock lock3 = redissonClient3.getLock("lock3");

RLock multiLock = redissonClient.getMultiLock(lock1, lock2, lock3);
multiLock.lock();   // 3 个都锁上才算成功

第七章：秒杀优化（异步下单）

7.1 传统秒杀的问题

text
请求进来 → 查库存（MySQL）→ 查一人一单（MySQL）→ 扣库存（MySQL）→ 创建订单（MySQL）
                                                              ↓
                                                        4 次 DB 操作，慢

7.2 优化思路：Redis 预校验 + 异步下单

text
请求进来 → Redis 预校验（纯内存，极快）→ 通过则生成订单 ID，推到消息队列，立即返回
                                              ↓
                                      异步消费：从队列读取，真正写 MySQL

7.3 Lua 脚本保证原子性

java
// Lua 脚本：判断库存 + 一人一单 + 扣库存，原子操作
String script =
    "local voucherId = ARGV[1]\n" +
    "local userId = ARGV[2]\n" +
    "local orderId = ARGV[3]\n" +
    "\n" +
    "local stockKey = 'seckill:stock:' .. voucherId\n" +
    "local orderKey = 'seckill:order:' .. voucherId\n" +
    "\n" +
    "-- 判断库存\n" +
    "if tonumber(redis.call('get', stockKey)) <= 0 then return 1 end\n" +
    "\n" +
    "-- 判断是否重复下单\n" +
    "if redis.call('sismember', orderKey, userId) == 1 then return 2 end\n" +
    "\n" +
    "-- 扣库存\n" +
    "redis.call('incrby', stockKey, -1)\n" +
    "-- 记录用户\n" +
    "redis.call('sadd', orderKey, userId)\n" +
    "-- 推送到消息队列\n" +
    "redis.call('xadd', 'stream.orders', '*', 'userId', userId, 'voucherId', voucherId, 'id', orderId)\n" +
    "return 0";

// 执行
Long result = stringRedisTemplate.execute(
    SECKILL_SCRIPT,
    Collections.emptyList(),
    voucherId.toString(),
    userId.toString(),
    orderId.toString()
);

// 0 = 成功，1 = 库存不足，2 = 重复下单
if (result != 0) {
    return Result.fail(result == 1 ? "库存不足" : "请勿重复下单");
}

第八章：面试常问（附答案）

Q1：缓存穿透、雪崩、击穿的区别？

答：

  • 穿透：查不存在的数据，穿到 DB
  • 雪崩：大量 key 同时过期
  • 击穿：热点 key 过期，瞬间大量请求

Q2：Cache Aside 为什么先改 DB 再删缓存？

答：先删缓存可能导致其他线程读到 DB 旧值并写回缓存。先改 DB 再删缓存，不一致概率极低。

Q3：分布式锁的三个问题？

答：

  1. 误删：存线程 ID，删前判断
  2. 不原子：用 Lua 脚本
  3. 不可重入：用 Redisson（Hash 存次数）

Q4：Redisson WatchDog 机制？

答：不设超时时自动启动，每 10 秒续期到 30 秒。进程崩溃不续期，锁自动释放。

Q5：超卖问题怎么解决？

答：乐观锁，WHERE stock > 0，一条 SQL 判断 + 修改。

Q6：秒杀怎么优化？

答：Redis 预校验（Lua 脚本）+ 消息队列异步下单。
