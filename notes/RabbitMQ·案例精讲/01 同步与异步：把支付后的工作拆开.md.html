01 同步与异步：把支付后的工作拆开

约 2 分钟阅读你的知识，慢慢成林

为什么课程引入MQ

支付成功后，交易服务要改订单状态，购物车服务可能要清理商品。同步调用像收银员依次打电话，所有人都答复才结束；消息队列像把工作单放入可靠的分发系统，各部门独立处理。

类比边界：现实工作单也会重复、延迟或无人处理。MQ降低时间耦合，却增加状态追踪与补偿成本。用户需要立即得到的支付结果不能简单改为“发消息就算成功”。

text
同步：支付 → 交易 → 购物车 → 返回
异步：支付本地事务成功 → 发布支付事件 → 返回支付结果
                                  ├─ 交易消费者更新订单
                                  └─ 购物车消费者清理条目

四个角色必须分清

生产者发送消息；交换机按规则路由；队列保存等待投递的消息；消费者处理队列里的消息。一个交换机可路由到多个队列。多个消费者监听同一个队列一般用于分担工作，不是每人都收到一份。

vhost像独立办公室，同名交换机和队列可以属于不同vhost。连接成功但收不到消息时，先核对双方是否进入同一个vhost、拥有所需权限。

第一次练习怎么做

使用课程mq-demo的publisher和consumer，先在管理界面创建一个练习队列，发送短字符串，再观察Ready和Unacked。Ready表示等投递；Unacked表示已投递但尚未确认，不等于正在数据库中成功提交。

java
// 片段：rabbitTemplate由课程Spring配置提供；learn.hello已声明
rabbitTemplate.convertAndSend("learn.hello", "hello, 小芽");

// 放在消费者Spring Bean中
@RabbitListener(queues = "learn.hello")
public void receive(String message) {
    System.out.println(message);
}

打印消息只能证明接收，不证明业务可靠。此处是理解流程的最小片段，连接配置、依赖、队列声明沿用课程工程。

自测与答案

题目：订单与购物车都要处理支付事件，应该共用一个队列吗？

答案：分别使用队列，由交换机把同一事件路由到两处。共用一个队列可能让订单拿走一条、购物车拿走另一条，无法保证两种业务各收到完整事件流。

完成标准：画出支付事件经过的交换机、两个队列和各自消费者。
