04 消费确认、重试与幂等：重复处理也不多扣一次

约 2 分钟阅读你的知识，慢慢成林

先理解两个AUTO不是同一件事

课程Spring容器的AUTO模式会在监听方法成功返回后进行确认；这不同于AMQP协议层的自动确认模式（投递后不再等待业务ack）。手动确认则由业务代码决定何时ack。

无论采用哪种方式，若把异常catch后只打印、方法正常结束，框架可能认为处理成功。失败应进入明确的重试/失败处理路径。

重试不是把错误永远转圈

临时网络抖动适合有限重试；JSON格式错误、缺少必填字段可能每次都失败，应转入错误队列供修正。nack/reject是否重新入队取决于requeue等设置，不能简单背“nack必重投、reject必丢弃”。

课程使用本地重试和RepublishMessageRecoverer，把耗尽重试的消息转到error.direct。错误队列还需要告警、查看原因、人工或自动修复、重新投递，不能把积压搬过去就算解决。

幂等要与业务事务一起做

支付事件重复到达时，只允许订单从待支付变为已支付。用条件更新避免旧支付消息把已退款订单改回已支付。

sql
-- 示例状态名用于解释，实际按课程表定义替换
UPDATE orders
SET status = 'PAID'
WHERE id = 1001 AND status = 'UNPAID';

受影响行数为0时应查明是已处理、订单不存在，还是非法状态。对于“增加余额”等不能靠状态转换处理的业务，可在同一数据库事务内插入唯一事件处理记录并执行业务修改。只先查“是否消费过”再执行，仍有并发窗口。

四格故障推演

故障时刻 应发生什么
数据库提交前崩溃 消息未确认，可再投递
数据库已提交、ack前崩溃 再投递，但幂等避免重复影响
重试耗尽 失败事件可追踪，进入修复流程
先ack后业务失败 可能失去自动重投机会，应避免

自测与答案

题目：给每次重试生成新eventId还能按eventId去重吗？答案：不能，新ID会被当成新事件。相同业务事件应保留稳定身份，或使用可靠业务唯一键去重。

完成标准：同一支付事件连续处理三次，最终订单状态正确、附带库存或余额操作只生效一次。
