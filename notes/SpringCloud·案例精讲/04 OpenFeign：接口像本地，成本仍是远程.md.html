04 OpenFeign：接口像本地，成本仍是远程

约 2 分钟阅读你的知识，慢慢成林

课程的声明式调用

Feign让HTTP调用写成Java接口，框架负责构造请求。像填写标准化申请单，不必手写信封，但邮件仍需运输；网络超时、失败、重试成本都还在。

java
// 概念片段：已启用@EnableFeignClients并接入课程服务发现
@FeignClient(name = "service-product")
public interface ProductClient {
    @GetMapping("/product/{id}")
    ProductDTO findById(@PathVariable("id") Long id);
}

路径与DTO需对应自己课程工程的实际接口。显式写参数名能减少反射参数名配置带来的歧义；不同服务不要靠复制内部实体无限耦合。

超时与重试按请求性质设计

连接超时是连不上，读取超时是连接后等响应太久。读取超时时对方可能已经完成业务，只是响应没回来。查询通常较容易重试；扣款、下单等写操作必须先有幂等键和重复请求语义。

text
调用A超时 → 不知道A是否已执行
        ├─ 安全查询 → 有界重试
        └─ 创建订单 → 使用请求唯一键查询/重试，避免创建第二单

每层都重试会放大流量：上游重试3次、下游每次再3次，可能产生9次请求。应有整体超时预算，不能只给每个服务各设一个很长超时。

降级返回要诚实

商品推荐查询失败，可返回“推荐暂不可用”；支付失败不能伪造成功。fallback的价值是限定故障影响，并保留可理解的结果，不是把所有异常吞掉。

课程练习

对目标接口增加仅用于练习的延迟，观察超时；暂停目标服务，观察失败；恢复后观察正常调用。记录真实调用次数，检查日志是否误输出token或完整个人信息。

自测与答案

题目：Feign方法返回失败，能说明数据库肯定没有写入吗？答案：不能，响应丢失也会导致调用失败。调用方要按业务协议确认结果。

完成标准：能给一个读接口和一个写接口分别设计超时、重试和降级行为。
