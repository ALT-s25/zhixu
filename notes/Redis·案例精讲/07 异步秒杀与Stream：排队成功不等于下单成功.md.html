07 异步秒杀与Stream：排队成功不等于下单成功

约 2 分钟阅读你的知识，慢慢成林

从课程的优化目标出发

同步秒杀请求等待查重、扣库存、写订单全部完成；课程将资格判断放到Redis，交给后台创建订单，缩短前台等待。类比是餐厅先取号再做菜：拿到号说明已受理，不说明菜已做好。

完整链路是：Lua原子判断库存和用户是否已买→扣Redis库存并记录用户→提交待处理事件→后台写数据库→成功后确认消息。Redis与MySQL之间不天然共享一个事务，必须考虑补偿。

三种队列对照

课程方式 优点 关键缺口
JVM阻塞队列 代码简单，方便理解异步 进程退出会丢内存任务
Redis List 可跨进程取任务 简单弹出后失败难恢复
Pub/Sub 在线广播方便 离线订阅者收不到历史消息
Stream消费者组 保存记录，支持待确认列表 仍需恢复、幂等与容量管理

最小Stream实验

redis
XGROUP CREATE learn:orders workers 0 MKSTREAM
XADD learn:orders * orderId 1001 userId 7 voucherId 101
XREADGROUP GROUP workers c1 COUNT 1 STREAMS learn:orders >
XPENDING learn:orders workers

>读取组内未投递的新消息。得到消息ID后，用实际ID替换下方占位文字，再执行确认：

text
XACK learn:orders workers <刚才返回的消息ID>

预期：读到消息但没ACK时pending为1；ACK后pending为0。ACK不等于从Stream物理删除消息，保留与裁剪需另外设计。重复执行XGROUP CREATE可能提示组已存在，这不是数据损坏。

可靠性的四个断点

  1. Redis已扣库存但没有可靠写入事件：会出现占用但无订单；资格与入队要一起设计。
  2. 消费者写库失败：不能ACK，应进入可恢复重试路径。
  3. 写库成功而ACK丢失：再次投递必须识别已存在订单，不能重复扣库存。
  4. 消费者永久下线：需要认领其pending消息，不能只反复读>。

自测与答案

题目：前台拿到orderId后就显示“购买成功”是否严谨？答案：异步系统中更合适的是“处理中”，再查订单状态；如果采用其他产品语义，必须有明确失败补偿和通知。

完成标准：能说清accepted、数据库已落单、ACK三个时刻。
