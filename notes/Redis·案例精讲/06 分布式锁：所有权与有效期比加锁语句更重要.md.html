06 分布式锁：所有权与有效期比加锁语句更重要

约 3 分钟阅读你的知识，慢慢成林

用共享钥匙理解，但别停在类比

多进程去同一处借钥匙，借到的人进入临界区。租期结束后钥匙可能借给别人，因此“我曾经拿到过”不等于“我现在仍拥有”。这就是课程从简单SETNX走向唯一标识和Lua解锁的原因。

redis
SET learn:lock:order:7 random-owner-token NX PX 10000

NX表示不存在才设置；PX把租期与加锁放在同一条命令里，避免成功加锁后、设置过期前进程崩溃。每次获取应使用唯一所有者标识。

为什么不能直接DEL

时间线：A加锁→A停顿超过租期→B加锁→A恢复并DEL。A误删B的锁，第三个请求就可能进入。先GET再判断再DEL仍有间隙，所以把比较与删除放进同一Lua脚本。

lua
-- KEYS[1]：锁key；ARGV[1]：本次持有者标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0  -- 已过期、已换主人或从未持有，都不删除

Redisson解决什么，没解决什么

课程继续讲可重入锁、重试和watchdog续期。可重入解决同一持有者再次进入的问题；续期减少业务尚未结束时租期届满的风险。显式指定固定租期与自动续期不是同一种使用方式，应按所用版本的API确认。

java
// 概念片段：lock 已由 RedissonClient 获取
boolean acquired = lock.tryLock(1, 10, java.util.concurrent.TimeUnit.SECONDS);
if (acquired) {
    try {
        // 完成受保护操作；此例明确使用10秒固定租期
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock();
    }
}

锁过期后旧持有者仍可能继续写数据库，正确解锁并不能撤回这些写操作。关键数据还应依靠条件更新、唯一约束、必要的版本/fencing机制。异步复制与故障转移也可能影响锁互斥，不能把单Redis锁描述成任何故障下都安全。

自测与答案

题目：Lua解锁保证了什么？答案：只保证检查所有权和删除之间不被其他Redis命令插入；不保证整段Java业务与数据库写入都原子，更不保证无限租期。

完成标准：能画出误删锁时间线，并解释为何SQL约束仍要保留。
